# M7.5b: Textures

**Status:** design, approved in conversation 2026-09-13.
**Milestone:** M7.5b, the textures half of the roadmap's "M7.5 Materials & textures".
**Predecessor:** M7.5a Materials, shipped v0.7.0 (v0.7.2 after two follow-up fixes).

## Context

M7.5a gave pluton a PBR-shaped material model: `Material(id, name, base_color, alpha,
metallic, roughness)`, independent front and back material slots per face, a sorted
translucent pass, undoable material editing, drag-to-paint, and a Color-by-Tag view mode.
Every material is still a flat colour.

Textures were deliberately excluded. The M7.5a design split the roadmap's single M7.5
entry in two, because textures cut the same layers again for a different reason and
because translucency's draw-order decision deserved undivided attention. That split is
what this document picks up.

Three issues have been waiting on it. `#64` (from M5b) asked for image-texture materials,
UV coordinates, a textured shader path and a positioning UI. `#78` (from M6a) reserved the
`.pluton` zip container's sibling-entry capability for texture assets and a thumbnail.
`#80` (from M6b) asked for the OBJ `vt` and `.mtl` map round-trip.

The starting position is genuinely empty. There is no UV storage in the C++ kernel, no UV
field anywhere in the Python model, and the glTF importer does not parse `TEXCOORD`. The
face vertex format is position plus normal, 24 bytes. The container holds `manifest.json`
and `document.json` and nothing else.

## 1. Scope

### 1.1 What ships

A material can carry an image. That image is projected onto every face painted with the
material at a real-world size, so a brick texture tiles at brick scale rather than
stretching to fit each face. A face can override the projection with its own offset, scale
and rotation, per side. The image tints with the material's `base_color`, and its alpha
channel makes cutouts genuinely see-through, drawing in the sorted translucent pass M7.5a
built. Textures are embedded in the document, so a `.pluton` file remains a single
portable artifact. The container also gains a thumbnail.

### 1.2 Where UVs come from

**Faces do not store UVs. They are projected.**

This is SketchUp's model rather than the one most 3D formats use, and the choice is
deliberate. A material carries a `texture_size`, the image's extent in model units. For
each face, a 2D basis is built on the face's own plane in definition-local space, each
corner is projected onto it, divided by `texture_size`, and then transformed by the
per-face placement if one exists.

Local space rather than world space means the texture is pinned to the geometry: moving or
rotating a group carries its textures with it rather than sliding them across the surface.

The consequence worth stating plainly is that a model imported with baked per-corner UVs
cannot be represented this way. That is why `#80` and glTF texture import are not in this
milestone. See section 5.

### 1.3 The texture model

```python
@dataclass(frozen=True, slots=True)
class Texture:
    id: int
    name: str                 # display name, from the source filename
    data: bytes               # the original encoded image, not a re-encode
    image_format: str         # "png" | "jpeg", as imported
    width: int                # pixels
    height: int               # pixels
    has_transparency: bool    # any non-opaque texel, computed once at import
```

`TextureLibrary` sits beside `MaterialLibrary` on `Model`, holding these by id with the
same add, edit, remove, restore and `index_of` shape M7.5a gave `MaterialLibrary`.

`Material` gains two fields:

```python
    texture_id: int | None = None
    texture_size: tuple[float, float] = (1.0, 1.0)   # model units
```

**The library holds encoded bytes and never decodes.** `pluton.model` is Qt-free and stays
that way. Decoding happens twice at the boundaries: once at import, to read the dimensions
and compute `has_transparency`, and once in the renderer, to upload the GL texture, which
caches the result by `texture_id` for the session. Holding decoded RGBA in the model would
be simpler and costs 16 MB for a single 2048 by 2048 image, which a scene with a dozen
textured materials cannot afford.

**The original bytes are stored, not a re-encode.** A photographic JPG re-encoded as PNG
grows by an order of magnitude, and a round trip through the document would be
generationally lossy. Storing the source bytes makes the round trip byte-exact.

### 1.4 Per-face placement

A face may override the material's default projection:

```python
@dataclass(frozen=True, slots=True)
class TexturePlacement:
    offset_u: float = 0.0
    offset_v: float = 0.0
    scale: float = 1.0
    rotation: float = 0.0    # radians
```

`scale` is **uniform**. Non-uniform sizing belongs on the material, where `texture_size`
already carries independent width and height in model units, and a face that needs a
differently-proportioned texture wants a different material rather than a squashed copy of
a shared one.

Storage follows the shape M7.5a established for face materials: a sparse sidecar on
`Scene` keyed by `(face_id, Side)`, holding only faces that have been adjusted. Most faces
never are, so the dict stays small and the serialized form stays additive.

Placement is **per side**, because M7.5a made front and back materials independent and a
face can therefore carry two different textures. Sharing one placement between sides would
mean adjusting the front visibly shifts the back, which contradicts that independence.

### 1.5 Rendering

**UVs are computed on the CPU at buffer-upload time and become a vertex attribute.** The
face vertex format grows from position plus normal to position, normal and UV: 6 floats to
8, 24 bytes to 32.

The alternative, computing UVs in the fragment shader from world position, needs the
face's plane basis and placement as uniforms. A batch spans many faces, so per-face
uniforms would collapse batching to one draw call per face. That trades away the structure
the whole renderer is built on.

Computing at upload works cleanly because `Scene.face_triangle_buffer` emits three
unshared vertices per triangle rather than an indexed mesh. Per-corner UVs are therefore
free, with no vertex splitting, which is the usual reason texture mapping is invasive.

**Batching does not change.** Batches already key on the `(front_material, back_material)`
pair, and a texture belongs to a material, so every triangle in a batch shares one front
texture and one back texture. Binding happens per batch, in the same place the material
uniforms already do.

**The shader gains two samplers**, front and back, matching the two uniform sets M7.5a
added for two-sided shading. The sampled colour multiplies the material's `base_color`, so
a white material shows the image unchanged and a coloured one tints it. The sampled alpha
multiplies the material's alpha.

**Translucency integrates through `has_transparency`.** That flag feeds the same
`_translucent_ids` set that `alpha < 1.0` already feeds, so a cutout texture lands in the
sorted second pass automatically. `Material.is_translucent` stays a cheap scalar read and
the pass M7.5a shipped is untouched.

**Placement changes force a re-upload.** Because UVs are baked into the vertex buffer,
changing a face's placement means rebuilding that definition's buffer. M7.5a built exactly
this mechanism for the translucency-set change: the relevant state is snapshotted on the
buffer at upload and compared on the next frame, and a mismatch re-uploads. Placement
state joins that snapshot rather than introducing a second mechanism.

### 1.6 The file format

Schema 5 to 6, additive. `document.json` gains texture records, `Material.texture_id` and
`texture_size`, and the placement sidecar. A schema-5 file loads with no textures and
`texture_id` `None` everywhere, so every v0.7.x document opens unchanged.

Image bytes are written as `textures/<id>.<ext>` sibling entries in the zip, which is the
capability `#78` reserved the container for. `document.json` references them by id.

The container also gains `thumbnail.png`, a small render of the current viewport, for file
browsers and a future Open dialog preview.

### 1.7 Editing

The Materials page gains a texture picker, a clear-texture button, and numeric
`texture_size` fields. A textured material's swatch renders the image tinted by
`base_color`, rather than the flat colour, so the picker does not misrepresent the result.

The Properties panel carries the per-face placement fields for the selected face and side.
This is the primary mechanism and covers the capability on its own. A drag-on-face
interaction for adjusting placement directly is a convenience over it, and is sequenced
last for that reason.

All mutations go through undoable commands following the `AddMaterialCommand` pattern: add
a texture, set a material's texture and size, set a face's placement.

**Deleting a texture clears every material that references it**, across the whole library,
and undo restores those references. M7.5a's `DeleteMaterialCommand` originally scanned a
single `Scene` and left dangling ids in other definitions that survived save and load;
texture deletion has the same shape one level up, with the references living on materials
rather than faces.

**Unused textures are kept.** A texture whose last material stopped referencing it stays in
the document, the way SketchUp keeps unused materials until an explicit purge.
Auto-deleting would make undo of a material edit unable to restore its image.

### 1.8 Error handling

Three cases, none of which may lose a document:

- An unsupported or corrupt image at import fails with a message and leaves the library
  unchanged.
- A `document.json` referencing a missing container entry loads that material untextured
  and warns, rather than refusing the file.
- A `texture_id` pointing at no record resolves to untextured, mirroring how
  `MaterialLibrary.get` already falls back to Default for an unknown id.

## 3. Testing

The projection, the placement transform and `has_transparency` are pure and testable with
no GL context and no `QApplication`. That is where the substantive coverage goes, and the
projection in particular wants tests that would fail against a plausible wrong basis
rather than restating the formula.

The GL path gets the recorder-based treatment M7.5a built for `render()`: a fake GL object
records the call sequence, so sampler binding and the UV attribute can be asserted
headlessly.

This milestone's entire subject is what things look like, so it ends with a **measured
offscreen pass**, not assertions: a textured face rendering the actual image, a cutout
texture showing background through it, and a per-face placement visibly moving the texture.
M7.4's visual pass found a defect 1800 tests missed, and M7.5a's found a winding bug that
had been invisible since `208384e`.

## 4. Decisions

- **D1.** UVs are projected, not stored. Faces carry no UV data.
- **D2.** Projection uses the face's own plane in definition-local space, so textures are
  pinned to geometry through moves and rotations.
- **D3.** A `TextureLibrary` holds encoded bytes plus metadata. The model layer never
  decodes and stays Qt-free.
- **D4.** Original encoded bytes are stored, not a re-encode, so round trips are byte-exact.
- **D5.** A texture tints `base_color` rather than replacing it, and its alpha multiplies
  the material's alpha.
- **D6.** `has_transparency`, computed once at import, feeds the existing translucent
  batching, so `is_translucent` stays a scalar read.
- **D7.** Per-face placement is per side, consistent with M7.5a's independent front and
  back materials.
- **D8.** UVs are computed at buffer-upload time as a vertex attribute, not in the shader
  from uniforms, because per-face uniforms would destroy batching.
- **D9.** Placement changes re-upload the definition, reusing M7.5a's buffer-snapshot
  mechanism rather than adding a second one.
- **D10.** Schema 6 is additive. Schema 5 documents load with no textures.
- **D11.** Unused textures are kept, not garbage-collected.
- **D12.** Deleting a texture clears references across the whole material library, undoably.
- **D13.** The thumbnail is written only when a viewport exists, so headless saves still work.

## 5. Out of scope

- **Imported per-corner UVs**, and therefore the OBJ `vt` and `.mtl` map round-trip (`#80`)
  and glTF texture import. These need UV storage on the mesh, which D1 excludes. They
  become **M7.5c**.
- **UV unwrapping** of any kind.
- **The four-pin Texture Position tool** with shear and perspective. M7.5b ships offset,
  scale and rotation.
- **Bump, normal, roughness and metallic maps.** One colour map per material.
- **Texture filtering and mipmap controls** beyond a sensible default.
- Order-independent transparency and real PBR shading remain M12.

## 6. Risks

**`QImage` without a `QApplication`.** Decoding at import may require a Qt application
instance. If it does, every headless test touching textures needs a Qt fixture, which
changes the testing story. This must be verified in the first task, not discovered late.
The fallback is decoding in the UI layer and handing the renderer a numpy array.

**Vertex format growth.** Every face vertex grows by a third, 24 bytes to 32, including in
documents with no textures at all. The alternative, two vertex formats selected per
definition, adds a branch to the hottest path in the renderer. Accepted as stated.

**The thumbnail needs a GL context at save time.** D13 makes it conditional, but the
interaction between save, the viewport's context and headless operation should be checked
early rather than assumed.

**`scene_renderer.py` is already about 1660 lines** and this milestone adds to it. Issue
`#109` tracks extracting its roughly 250 lines of GL-free logic. Doing that extraction
before or early in this milestone would make the texture work land in a smaller file.

## 7. Sequencing

Model and projection first, because they are pure and everything else consumes them:
`Texture` and `TextureLibrary`, then `uv_projection`, then the placement sidecar on
`Scene`. Then the renderer: vertex format, texture cache, shader, sampler binding. Then
persistence, schema 6 and the container entries. Then editing: commands, the Materials
page, the Properties fields. The thumbnail and the drag-on-face interaction come last,
being the two most severable pieces.

| 2026-09-13 | Rowee Apor | Execution closed out, with nine points recorded against this spec, all verified. Section 6 named `QImage` needing a `QApplication` as the largest risk; it does not need one, verified before this document's first task began and re-verified in an isolated subprocess during execution (a `QApplication` is process-global and never goes away once another fixture has built one, so proving the claim in-process would have been order-dependent), so no Qt fixture was ever needed for a texture test. `QImage.hasAlphaChannel()` reports the image *format*, not whether any texel is actually non-opaque; trusting it would have put every opaque RGBA image into the sorted translucent pass, so `has_transparency` scans the alpha channel instead. Section 1.4 and D7 mandate per-side placement with an explicit rationale, while 1.5 mandated a single UV attribute at 8 floats, 24 to 32 bytes; two-sided shading draws both sides in one pass selected by `gl_FrontFacing`, so one UV attribute makes back placement physically unrepresentable, which would have left the placement command, the Properties fields and the drag interaction all carrying a dead `side` parameter that could never do anything. Resolved during execution: the face vertex carries two UV sets, 10 floats and 40 bytes, front at attribute location 2 and back at location 3, selected by `gl_FrontFacing` exactly as the material uniforms already are; 1.5's "8 floats, 24 to 32 bytes" is superseded by this. Baking UVs made buffer upload about 16 times slower before it was fixed: on a 9,600-face definition, upload went from 19.0 ms to 305.0 ms, with the bake alone 94% of the total, and the cost was the per-face Python loop, not the arithmetic. Vectorising the projection across faces brought the total to 78.7 ms with both sides baked; `uv_projection.py` keeps its scalar functions as the reference implementation, with the batched versions pinned to them by an equivalence test. `Scene.face_normal` raises `ValueError` when a face's first three loop vertices are collinear, which is exactly what an edge split leaves behind; baking UVs briefly put that call on the render path, where one such face would have stopped the whole document from rendering, so the render path now takes the normal from the block `face_triangle_buffer` already returns instead of calling `face_normal` again. That defect is pre-existing and is not fixed by this milestone; it remains reachable from six interactive callers (`push_pull_tool`, `offset_tool` twice, `paint_tool`, `rotate_tool`, `geometry/plane.py`, `model/model.py`). D11 is honoured and carries a consequence worth stating on its own: `DeleteTextureCommand` exists, is correct and is fully tested, but nothing in the UI reaches it, so a `.pluton` file accumulates every image ever imported into it. D11 already says unused textures are kept "until an explicit purge"; that purge is not built. Textures persist with a `next_id`, in the same shape as the material, tag and view libraries, rather than as a bare list; without it, deleting the highest-id texture, saving and reloading would regress `next_id` and let a new texture reuse the freed id, which materials reference by `texture_id`. The Properties panel owns a Front/Back control rather than following the spec's phrasing of fields "for the selected face and side": no selected-side concept exists anywhere in the application, `Selection` carries no side, and only the Paint tool resolves one transiently from a pick ray, so the placement group itself owns which side it edits rather than adding a side to `Selection`, and the fields are enabled only when exactly one face is selected. A positive placement `rotation` turns the image **clockwise** on screen, which is the opposite of the convention a reader might expect and is deliberate: the value rotates the UV frame, and rotating a frame counter-clockwise makes the image sampled through it appear to rotate clockwise, so the behaviour is mathematically correct rather than a defect. The Properties label is a bare "Rotation" in degrees, so nothing in the interface promises the other direction. The sign is persisted in every saved placement, so it is frozen the moment v0.8.0 files exist: flipping it later would silently re-rotate every texture in every document already saved, to satisfy a UX preference nobody has stated. It stays as it is, and this is the record of that choice. |
