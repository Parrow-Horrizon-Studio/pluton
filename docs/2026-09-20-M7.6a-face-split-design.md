# M7.6a: Face split

**Status:** design, approved in conversation 2026-09-20.
**Milestone:** M7.6a, the first of three sub-milestones the roadmap's "M7.6 Interaction parity" splits into.
**Predecessor:** M7.5c UV storage and texture round-trip, shipped v0.9.0.
**Siblings:** M7.6b inferencing, construction guides and on-canvas measurement. M7.6c smart-select.

## Context

M3d's design closed with one sentence that has stood unresolved ever since: face-split is
deferred to Phase 2. Phase 2 came and went, Phase 2.5 is nearly over, and drawing a line
across a face still does nothing to the face. The edge lands, it is visible, it is
selectable, and the face underneath it stays whole. Push/pull one half and the other half
comes with it, because there is no other half.

That is the last structural gap between pluton and the SketchUp interaction it models. The
kernel can already merge two faces into one: `HalfEdgeMesh::dissolve_edge`
(`cpp/include/pluton/halfedge.h:104`) splices two boundary loops across a shared edge and
has done since M3c. Nothing can divide one face into two. `split_face` is that operation's
inverse and it does not exist anywhere in `cpp/`.

The gap has a second half that is easy to miss. The Eraser today **deletes** both faces
incident to an erased edge (`python/pluton/tools/erase_tool.py:3-5`, "a face can't survive
losing a boundary edge"), and `DissolveEdgeCommand` is reachable only from push/pull's
internal coplanar seam merge (`python/pluton/tools/sweep_support.py:120`). Ship the split
on its own and the obvious way to undo it by hand, erasing the line you just drew, destroys
both halves and leaves a hole. Split without merge is a trap, so this milestone carries
both.

## 1. Scope

### 1.1 What ships

Drawing a path across a face divides it, and erasing the cut puts it back.

Three pieces: a kernel operation, tool wiring that decides when to call it, and an Eraser
that dissolves a coplanar interior seam instead of cascading through it. No new entity,
no new panel, no schema change.

### 1.2 The split trigger

The Line tool already holds the only state this needs. `line_tool.py:111` opens a gesture
with `self._gesture_vertex_ids = [vid]` and appends to it as the polyline grows, and
`:107` opens a `CompositeCommand(name="Draw Line")` that every command of the gesture
composes into. The chain is therefore known, in order, by the tool, at the moment the
gesture ends.

On gesture end, whether by Enter, Esc, double-click, or snapping back onto the first
vertex, the tool asks whether its chain cuts a face:

1. Take `first = chain[0]` and `last = chain[-1]`. If they are equal the gesture closed a
   loop, which is the existing face-creation path and never a split.
2. Candidate faces are those incident to `first` **and** incident to `last`, with both
   vertices present on the candidate's boundary loop. An endpoint that snapped mid-edge is
   already a loop vertex by this point, because `line_tool.py:297` ran `SplitEdgeCommand`
   when it resolved the snap.
3. Reject a candidate unless every interior vertex of the chain lies in that face's plane
   within `_DIST_TOL` and strictly inside its polygon, and unless **every segment's
   midpoint** lies strictly inside the polygon. The per-segment midpoint test is what
   rejects a chain drawn outside the face or along its boundary, and for a two-vertex chain
   it is the only containment test there is, since such a chain has no interior vertex.
4. Exactly one candidate should survive, because a point interior to a manifold surface
   belongs to one face. If none survives, no split. If more than one survives, no split:
   that means two coplanar faces overlap, which is a degenerate mesh this milestone
   declines to guess about.

The Arc tool takes the identical path. A two-point arc tessellates into an open chain of
segments, so it is the same gesture with more vertices, and sharing the mechanism costs
only the shared helper both tools call.

### 1.3 The kernel operation

```cpp
/// Replace face f_id with two faces that share a chain of vertices.
/// loop_a and loop_b are the two new boundary loops, each already
/// triangulated by the caller, exactly as add_face_from_loop expects.
/// Returns {id_a, id_b}, or {INVALID_ID, INVALID_ID} if any precondition
/// fails, in which case the mesh is untouched.
std::array<std::uint32_t, 2> split_face(
    std::uint32_t f_id,
    const std::vector<std::uint32_t>& loop_a, const std::vector<std::int32_t>& tris_a,
    const std::vector<std::uint32_t>& loop_b, const std::vector<std::int32_t>& tris_b);
```

The implementation is `remove_face(f_id)` followed by two `add_face_from_loop` calls, which
is exactly what the kernel's own `split_edge` does at `cpp/src/halfedge.cpp:813-814`. The
new work is not the surgery, it is the validation in front of it:

- `f_id` is live.
- `loop_a` and `loop_b` each have at least 3 vertices.
- The vertices shared by both loops form one contiguous run in each, of length at least 2.
  That run is the chain, and its two ends are its only members that lie on `f_id`'s loop.
- Deleting the chain's interior from both loops and concatenating what remains reproduces
  `f_id`'s boundary loop as a cyclic sequence, in the same winding.
- Every triangle index refers to a vertex of its own loop.

Two things justify this living in the kernel rather than in a Python command that calls
`remove_face` and `add_face_from_loop` itself. Every topology operation pluton has
(`split_edge`, `dissolve_edge`, `add_face_from_loop`) lives in the kernel, and this is the
last major one missing, so putting it in Python would leave one op out of four in the wrong
language and reaching through `Scene` into `_mesh`, which `#26` already flags as debt worth
removing rather than adding to. And it is **atomic**: validation runs before the first
mutation, so a rejected split leaves the mesh exactly as it was, where a Python sequence
that removed the face and then failed to rebuild one of the halves would leave a hole.

### 1.4 Sub-loop construction

Python owns this, because the triangulator is in Python and `add_face_from_loop` already
takes a caller-supplied triangulation.

Given the parent's cyclic loop `L` and the chain `C = [c0, ..., ck]` with `c0` and `ck` in
`L`, let `P` be the forward walk of `L` from `c0` to `ck` and `Q` the forward walk from
`ck` back to `c0`. Then:

```
loop_a = P + reversed(C[1:k])
loop_b = Q + C[1:k]
```

Both preserve `L`'s winding, which is what keeps both children's normals pointing the way
their parent's did. This matters beyond appearance: six interactive tools push, offset and
paint along the face normal, and M7.5a gives the back side its own material slot, so a
flipped child would come back as the deliberate grey of an unpainted reverse face.

Each sub-loop is triangulated through the same path `Scene.add_face_from_loop` already
uses at `scene.py:224`: project onto the dominant axis-aligned plane via
`_project_loop_to_2d_for_earcut`, then `mapbox_earcut.triangulate_float32`. No second
triangulation convention is introduced.

The Python entry point is `Scene.split_face(f_id, chain) -> tuple[int, int] | None`,
mirroring `Scene.split_edge`'s shape: build the loops, triangulate, call the kernel,
transfer the sidecars, return the new ids or `None`.

### 1.5 Sidecar transfer on split

This goes through M7.5c's shared transfer point, so it cannot drift from what `split_edge`
does. That family currently has two members, and this adds a third, because the three cases
are genuinely different shapes and one function pretending to serve all three would be
worse than three named ones:

| Case | Member | The new loop, relative to the old |
|---|---|---|
| Rebuilt verbatim (Make Group, Explode, Make Unique) | `copy_face_attributes_from` | identical |
| Edge split | `_transfer_face_attributes` | grew by one corner, on a known edge at a known `t` |
| **Face split** | **`_transfer_subloop_face_attributes`** | **a contiguous arc of the old loop, plus a chain of vertices that were not on it** |

Front and back material and placement copy to both children unchanged. A split divides a
surface; it does not repaint it.

Stored per-corner UVs need a value for every corner of each child, and the chain's interior
vertices have no corresponding corner in the parent. Each such vertex is resolved by
**barycentric interpolation inside the parent's own triangulation**: find the parent
triangle containing the vertex (it lies in the parent's plane and strictly inside its
polygon by 1.2's test, so one exists), and interpolate the three corners' stored UVs.

The alternative, fitting an affine map from the parent's plane to its UV layout and
evaluating it, is cheaper and is exact whenever the layout came from pluton's own planar
projection. It is wrong for an imported layout, which is precisely what M7.5c spent a
milestone adding, and getting it wrong would silently distort exactly the models that
milestone existed to support. Barycentric interpolation is exact for any triangulated
layout and reduces to the affine answer when the layout is affine.

A child whose parent had no stored UVs gets none, and falls back to the projection.

### 1.6 Erase to merge

`erase_tool.py:115-122` composes one edge's removal as "remove incident face(s) first, then
the edge". A test is inserted in front of that cascade. Dissolve instead of cascading when
all of the following hold:

- the edge has exactly two live incident faces,
- `Scene.faces_are_coplanar(f1, f2)` is true under the project tolerances
  (`scene.py:399`, `cos(0.5°)` and `1e-4`),
- `dissolve_edge`'s own preconditions hold, which is to say the two faces share exactly
  this one edge. The kernel already checks this and returns `INVALID_ID` otherwise
  (`halfedge.cpp:659-669`), so the tool treats a returned `INVALID_ID` as "fall back to the
  cascade" rather than duplicating the check.

Otherwise cascade, exactly as today. A boundary edge with one face, a seam between two
faces at an angle, and an edge shared twice all keep their current behaviour.

The coplanarity test is what stops this from being surprising. Erasing the crease of a
folded surface still deletes both faces, because merging them would produce a face the
kernel's planar assumption does not hold for.

`DissolveEdgeCommand` already exists (`scene_commands.py:246`) and already composes into a
command stack, so the erase stroke's existing single-undo behaviour is preserved by routing
through it rather than by new machinery.

This also repairs something that predates the milestone: erasing an interior seam left
behind by push/pull's coplanar merge has always deleted both faces, and after this it
merges them.

### 1.7 Sidecar transfer on merge

M7.5c's **D4a** ruled that `dissolve_edge` leaves all four face-keyed sidecars alone, on
the grounds that a merge has two candidate sources and no defensible winner. That was
correct while dissolve was reachable only from push/pull's internal seam merge, where the
merged face is an implementation detail the user never named.

It stops being correct the moment erasing a cut is a user gesture. Split a painted wall,
erase the line, and D4a hands back an unpainted wall. The round trip has to be lossless,
and in that round trip both halves inherited from one parent, so they always agree.

**D4a is revised: agree-or-drop.** For each of the four sidecars, if both parents carry the
same value the merged face keeps it; if they differ, the merged face carries nothing and
falls back to the default. Absence counts as a value (material id 0, Default) and therefore
as a disagreement, so merging a painted face into an unpainted one yields an unpainted face
rather than silently spreading the paint across geometry the user never painted.

Per-corner UVs follow the same rule at corner granularity: both parents must have stored
UVs, and they must agree at every vertex the merged loop takes from both; otherwise the
merged face has none. When they do agree, the merged loop's UV array is gathered
vertex-wise from whichever parent carried each corner.

### 1.8 Persistence

None. A split produces ordinary faces and a merge produces an ordinary face. `.pluton`
stays at `schema_version` 7 and v0.9.0 files open unchanged.

## 3. Testing

**ctest.** `split_face` is the first kernel operation added since M7.4, so this is where the
C++ coverage moves. Each precondition gets a case that fails it and asserts the mesh is
untouched afterwards, which is the atomicity claim 1.3 makes. Beyond those: a chord split
of a quad, a split whose chain has interior vertices, sequential splits of the same face
(which also closes `#31`'s outstanding `split_edge` GoogleTest item, since the same fixture
serves both), winding preservation in both children, and a split followed by
`dissolve_edge` of a chain edge returning to a face with the parent's loop.

**pytest.** The chain-cuts-a-face test gets the cases 1.2 enumerates, each one written to
fail against an implementation missing that check: a chain whose endpoints are on different
faces, a chain drawn outside the polygon, a chain whose interior leaves the plane, a
closing loop. Sidecar transfer gets a split of a face carrying a **stored** UV array and
asserts the chain vertex's interpolated UV, which is the assertion that discriminates
barycentric interpolation from an affine fit, so the fixture must use a layout where the
two disagree. The Eraser gets the dissolve case, the non-coplanar cascade case, and the
boundary-edge cascade case.

**Visual gate.** The house rule that every renderer-visible milestone closes with a
render-and-look pass applies. Split a **textured** face and confirm the texture does not
jump, shift or mirror across the cut, then erase the cut and confirm it comes back
continuous. A wrong barycentric interpolation moves texels without changing any count, any
length, or any test that compares numbers to numbers, which is the same class of defect
M7.5c's V-flip was and the reason that gate exists. The gate must be shown to discriminate,
by perturbing the interpolation and confirming the render changes.

## 4. Decisions

**D1.** Chord splits only. A path that runs boundary to boundary across a face divides it.
A closed loop drawn strictly inside a face does not, because the outer remainder would be a
ring and the kernel's `Face` is a single boundary loop. See 5.

**D2.** The cutting path is recognised from the drawing tool's own gesture state, not by
searching the mesh. `line_tool.py` already tracks `_gesture_vertex_ids`, so a one-segment
cut and an L-shaped multi-segment cut are the same mechanism, because they are one gesture.

**D3.** The topology surgery is a C++ kernel operation. Rationale in 1.3: every other
topology op is there, and validation-before-mutation makes a rejected split atomic.

**D4.** Python builds and triangulates the two sub-loops and passes them in. The
triangulator is in Python and `add_face_from_loop` already takes a caller-supplied
triangulation, so the alternative would mean a second triangulation convention in C++.

**D5.** Both children inherit the parent's material and placement on both sides. A chain
vertex's stored UV is resolved by barycentric interpolation inside the parent's
triangulation, not by fitting an affine map, because the affine answer is exact only for
pluton's own projection and wrong for the imported layouts M7.5c added.

**D6.** The transfer family gains a third named member rather than generalising the
existing two. The verbatim, grown-by-one and subloop cases have different shapes, and a
single function serving all three would take arguments that are meaningless in two of them.

**D7.** Erasing an edge dissolves when its two faces are coplanar and share only it, and
cascades otherwise. Without this the obvious way to undo a split by hand destroys both
halves.

**D8.** D4a is revised to agree-or-drop, for the reason in 1.7. Absence counts as
disagreement, so a merge never spreads paint onto geometry the user did not paint.

**D9.** No persistence change. Splits and merges produce ordinary faces.

## 5. Out of scope

**Interior islands.** A rectangle, circle or polygon drawn strictly inside a face does not
split it. This is the most visible gap against SketchUp and it is deliberate: the outer
remainder is a ring, and representing one needs either multi-loop faces in the kernel,
which every consumer of `face_loop_vertices` would have to learn about, including the
triangulator, the UV bake, and both exporters, or a bridge edge spliced into the outer
loop, which is a real edge the user can see and erase. That fork is worth deciding with a
user asking for it rather than in advance. **Filed as its own issue carrying both options.**

**Paths assembled across separate gestures.** Draw half a cut, press Esc, draw the rest
later: no split, because D2 reads gesture state and the gesture ended. A mesh-side path
search would fix it and costs a geometric query the kernel does not have, since an edge
drawn across a face has no face pointer at all.

**Non-planar results.** A chain whose interior leaves the face's plane is rejected rather
than producing two non-planar children.

**Splitting from anything but Line and Arc.** The other drawing tools produce closed loops,
which are islands, which are out of scope above.

## 6. Risks

**The winding argument is load-bearing and easy to get subtly wrong.** A child built with
reversed winding renders as an unpainted back face and pushes the wrong way. 1.4's
construction preserves it by walking the parent loop forward in both halves, and a ctest
asserts both children's normals against the parent's.

**The barycentric fixture can be blind.** A split of a face whose UV layout happens to be
affine passes with either implementation. The test must use a layout where affine and
barycentric answers differ, and must be confirmed to fail against the affine one.

**The Eraser's new conditional changes behaviour users already rely on.** Erasing a
push/pull seam merges now where it deleted before. That is the better behaviour and it is
what SketchUp does, but it is a behaviour change to an existing tool rather than a new
feature, and it should be called out in the milestone's notes rather than discovered.

**`dissolve_edge` after a multi-segment split leaves stray edges.** Erasing one segment of
an L-shaped cut merges the two faces and leaves the other segments as interior edges of the
merged face, attached at both ends to its loop. This matches SketchUp and is not a defect,
but it will look like one to anyone who expects erasing part of a cut to remove all of it.

## 7. Sequencing

1. `split_face` in the kernel with its validation and GoogleTest coverage, plus the binding.
   Nothing above it exists yet, so this stage is provable entirely from ctest.
2. `Scene.split_face`: sub-loop construction, triangulation, and `SplitFaceCommand` with
   undo. Still no tool wiring, so still headlessly testable.
3. `_transfer_subloop_face_attributes` and the barycentric UV resolution.
4. Line and Arc wiring through the shared chain test, plus `#31`'s double-click finish.
5. Eraser dissolve-or-cascade and the revised merge-side sidecar rule.
6. Visual gate, then the milestone notes and the island issue.

Stages 1 through 3 are independently reviewable and none of them changes what the
application does, which makes the first user-visible change stage 4, after the machinery
under it is already covered.
