# M7.2 — UI Shell (Design)

**Milestone:** M7.2, the second sub-milestone of **Phase 2.5 — Parity & Polish**, following M7.1 (Triage & burn-down, shipped v0.3.0) and preceding M7.3 (Outliner & Properties panel).

**Goal:** Give Pluton the surface of a real application — SketchUp-style dockable toolbars driven by an original icon set, per-tool cursors, and context-sensitive right-click menus — without changing what the application can do. Ship as **v0.4.0**.

**Shape:** Python-only, presentation-only. No kernel change (`ctest` stays 82/82), no new undoable commands, no document-format change. The two genuinely new behaviours (Select All, Zoom Extents) live entirely in the selection and camera layers.

---

## Context: why this milestone exists

v0.3.0 is a capable modeler with an unusable shell. Eighteen tools ship, but only **five** appear in a menu; the other thirteen are reachable only by knowing an undocumented single-letter shortcut. Nothing on screen indicates which tool is armed. The cursor is the same arrow for every tool. Right-click does nothing at all.

There is also a structural reason to do this now. The Wall tool's `W` shortcut is currently written in **three** places — `WallTool.shortcut`, a `QShortcut(QKeySequence("W"))` in `main_window`, and the literal `"Wall\tW"` in the Tools menu. Adding a toolbar button and a context-menu entry naively would make it five, times eighteen tools. M7.2 collapses that to one declaration before M7.3 adds a whole panel to the same file.

`main_window.py` is 1152 lines. This milestone must leave it **smaller** than it found it.

## 1. Scope

### 1.1 Architecture — a declarative action registry

Every user-invokable command is declared exactly once, as data, in a Qt-free `pluton/ui/actions.py`:

```python
@dataclass(frozen=True, slots=True)
class ActionSpec:
    id: str                        # "tool_line", "file_save", "view_zoom_extents"
    label: str                     # menu text, e.g. "Line"
    handler: str                   # MainWindow method name, e.g. "_on_tool_line"
    icon: str | None = None        # None for menu-only actions; otherwise equal to `id`
    shortcut: str | None = None    # "L", "Ctrl+S", "Shift+Z"
    checkable: bool = False
    group: str | None = None       # QActionGroup key: "tool" | "face_style"
    cursor: CursorStyle | None = None   # tools only
    tooltip: str | None = None     # defaults to f"{label} ({shortcut})"
```

`ToolbarSpec(id, title, action_ids)`, `MenuSpec(title, action_ids)`, and the context-menu tables reference actions **by id**; a `None` entry means a separator. Label, icon, shortcut, and tooltip are therefore identical in every surface by construction.

Because `actions.py` imports no Qt, the entire UI taxonomy is testable without a `QApplication`.

Thin builders consume the registry and are the only code that touches Qt widget construction:

- `build_menubar(window, handlers) -> None`
- `build_toolbars(window, handlers) -> dict[str, QToolBar]`
- `build_shortcuts(window, handlers) -> None`
- `context_menu_ids(target, *, in_group, has_selection) -> tuple[str | None, ...]` (pure)

`handlers` resolves each `ActionSpec.handler` name against the `MainWindow` instance via `getattr`. `MainWindow` retains only handler methods and application state.

**Keeping the registry honest.** `Tool.name` and `Tool.shortcut` remain authoritative for tools. `actions.py` deliberately does not import the tool modules (that would pull Qt in transitively and defeat the headless property), so the two are pinned by a test that asserts every tool `ActionSpec` matches the corresponding registered `Tool` instance's `name` and `shortcut` exactly. Drift fails the suite.

### 1.2 Toolbars

Seven dockable, floatable `QToolBar`s, following SketchUp's grouping with one Pluton-specific addition:

| Toolbar id | Title | Contents (⋮ = separator) |
|---|---|---|
| `standard` | Standard | New · Open · Save ⋮ Undo · Redo ⋮ Zoom Extents |
| `principal` | Principal | Select · Eraser · Paint |
| `drawing` | Drawing | Line · Rectangle · Circle · Polygon · Arc |
| `modification` | Modification | Push/Pull · Move · Rotate · Scale |
| `construction` | Construction | Tape Measure · Dimension · Text |
| `architecture` | Architecture | Wall · Door/Window · Roof |
| `styles` | Styles | Wireframe · Hidden Line · Monochrome · Shaded ⋮ X-Ray |

All eighteen tool actions are `checkable=True, group="tool"` and share one `QActionGroup`, so the armed tool is visibly depressed — closing a real gap, since nothing currently indicates the active tool. The four face styles form a second exclusive group (`group="face_style"`); X-Ray is an independent checkable toggle. All are re-presentations of commands that already work through `_activate` and the existing View-menu style handlers.

Zoom Extents joins **Standard** rather than getting a one-button Views toolbar: Pluton has no preset camera views, and inventing Top/Front/Iso here would be scope creep.

`View ▸ Toolbars` gains a checkbox per toolbar via `QToolBar.toggleViewAction()`, plus **Reset Toolbars**.

The existing menu bar (File, Edit, Units, Tools, View) is rebuilt from the registry. Content is preserved except for four additions: the **Tools menu lists all eighteen tools** rather than five, **Edit** gains Select All, and **View** gains Zoom Extents plus the Toolbars submenu and Reset Toolbars. The Units menu's mutually-exclusive entries join the registry as a third `QActionGroup` (`group="units"`), so the registry's "declared once" property holds for the whole menu bar.

Two menu items stay outside the registry because they are generated from live objects rather than declared: the **dock toggles** (Materials, Tags, Scenes) and the per-toolbar checkboxes both come from Qt's own `toggleViewAction()`. Both are appended to the View menu after the registry-driven entries.

### 1.3 The icon set — 29 original icons

18 tools + 6 Standard (New, Open, Save, Undo, Redo, Zoom Extents) + 5 Styles (Wireframe, Hidden Line, Monochrome, Shaded, X-Ray).

Original work, authored as SVG path data in-repo. No third-party icon pack — a branding choice and a licensing simplification.

**Fixed spec, so all 29 stay coherent:**

- **24×24 viewBox**, 2px padding, giving a **20×20 live area**
- **Monochrome**, single flat fill, recolored at load from the Qt palette's text color (`QPainter.CompositionMode_SourceIn`), so one asset set serves light and dark themes
- **1.5px stroke width**, geometric forms only, snapped to the pixel grid
- **Restricted SVG subset:** only `path`, `line`, `circle`, `rect`, `polyline`, `polygon`, and `g`. No gradients, filters, `text`, embedded images, CSS, or scripts
- **Filename = action id**, snake_case, `.svg`: `tool_line.svg`, `tool_push_pull.svg`, `file_save.svg`, `view_zoom_extents.svg`, `style_xray.svg`

**Drawing language.** Tool icons depict the *result*, not the gesture — Rectangle is a rectangle, Circle a circle, Wall a plan-view double line, Roof a gable profile — with an accent mark only where two tools would otherwise be indistinguishable (Move's four-way arrow, Rotate's arc-arrow, Scale's corner grip). Push/Pull is a face with an extrusion arrow: the one icon that must read as a verb.

**Storage and loading** follow the pattern already proven by shaders (`scene_renderer.py:198`): assets live beside their package and load through `importlib.resources`.

```python
# icons.py
(files("pluton.ui") / "icons" / f"{stem}.svg")
```

`icon(stem) -> QIcon` caches by `(stem, palette_color)`. A missing stem **raises** rather than returning an empty `QIcon`, so a typo fails loudly in tests instead of shipping a blank button. No `.qrc`, no `pyside6-rcc` build step, no packaging change.

### 1.4 Cursors

`compose_cursor(base, icon, hotspot) -> QCursor` paints the tool's glyph, scaled to 16×16, into the lower-right of a 32×32 base pixmap, DPI-aware via `setDevicePixelRatio`. Cursors are therefore *derived from* the icon set, not a second art pipeline, and stay in sync automatically when an icon changes.

Two bases, matching SketchUp's own split:

| `CursorStyle` | Base | Hotspot | Tools |
|---|---|---|---|
| `CROSSHAIR` | crosshair centred at (11,11) | (11,11) | Line, Rectangle, Circle, Polygon, Arc, Move, Rotate, Scale, Tape Measure, Dimension, Text, Wall, Door/Window, Roof |
| `ARROW` | arrow anchored at origin | (0,0) | Select, Eraser, Paint, Push/Pull |

The split is semantic: crosshair tools *place a point* and need a precise hotspot; arrow tools *pick an entity*, where a crosshair would imply an accuracy that is not being used. The arrow base is drawn by Pluton rather than taken from the OS, so the cursor looks identical on Windows and Linux.

`cursor` lives on `ActionSpec`, **not** on the `Tool` ABC: cursors are presentation, tools have no business importing `QCursor`, and this avoids editing all eighteen tool classes.

The cursor is set on the viewport widget only (`_activate` applies it), so it reverts normally over docks, menus, and the option bars.

### 1.5 Context menus

A pure function returns action ids; a thin builder turns them into a `QMenu`.

```python
def context_menu_ids(
    target: ContextTarget, *, in_group: bool, has_selection: bool
) -> tuple[str | None, ...]: ...
```

`ContextTarget` is an enum: `FACE`, `EDGE`, `INSTANCE`, `ANNOTATION`, `EMPTY`.

| Target | Entries |
|---|---|
| `FACE` | Erase ⋮ Make Group · Make Component… ⋮ Paint |
| `EDGE` | Erase ⋮ Make Group · Make Component… |
| `INSTANCE` | Edit Group · Erase ⋮ Explode · Make Unique ⋮ Assign Tag ▸ |
| `ANNOTATION` | Erase · Edit Text… |
| `EMPTY` | Select All · Select None ⋮ Close Group ⋮ Zoom Extents |

**`Assign Tag` appears on `INSTANCE` only.** M5c shipped instances-only tagging; loose edge/face tagging is deferred to [#69](https://github.com/Parrow-Horrizon-Studio/pluton/issues/69). Offering it on a face would present a control that cannot work.

Hit-testing reuses the existing `pick_instance` / `pick_selectable` / annotation draw-plan paths — no new picking code. Right-clicking an **unselected** entity selects it first, then opens the menu (SketchUp's behaviour). Right-clicking **empty space leaves the selection untouched**; `Select None` is present in that menu for the explicit case.

Inapplicable entries are **disabled, not hidden** — `Make Unique` only for component instances, `Explode` only for group/component instances, `Close Group` only when `in_group` — so entries never change position between right-clicks.

This ships the context-menu half of [#73](https://github.com/Parrow-Horrizon-Studio/pluton/issues/73). Its Entity-Info half belongs to M7.3's Properties panel, so **#73 stays open** rather than being over-claimed.

### 1.6 Select All and Zoom Extents

Neither exists today. Both are UI/camera-layer only — no kernel, model, or command-stack change.

Both read-only model queries live together in a new `python/pluton/model/model_queries.py`; the pure camera math lives in `python/pluton/viewport/camera_framing.py` and imports no model type at all.

**Select All** (`Ctrl+A`, Edit menu + `EMPTY` context menu):

```python
# model/model_queries.py
def select_all_ids(model) -> tuple[set[int], set[int], set[int]]:  # edges, faces, instances
```

Scoped to the **active editing context** only, matching how every other operation behaves, and skipping instances hidden by tag visibility so it agrees with `traverse_visible`. Feeds the existing `Selection.replace()`.

**Zoom Extents** (`Shift+Z`, View menu + Standard toolbar + `EMPTY` context menu). Two pure functions:

```python
# model/model_queries.py
def model_bounds(model) -> tuple[np.ndarray, np.ndarray] | None: ...

# viewport/camera_framing.py  — plain arrays in, plain arrays out
def frame_bounds(bmin, bmax, view_dir, aspect, fov_y) -> tuple[np.ndarray, np.ndarray]:
    """Returns (position, target)."""
```

`model_bounds` walks `traverse_visible`, returning `None` for an empty scene. `frame_bounds` preserves the camera's current view **direction**, moving along it until the bounding sphere fits with a small margin, and returns the new position and target for the camera to adopt. An empty scene is a no-op; a single-point or zero-extent model is clamped to a minimum radius so no division by zero is possible.

This mirrors M7e's `interpolate_pose`: pure numpy, headlessly tested, with the Qt/camera layer merely applying the result.

### 1.7 Window-state persistence

Pluton's first non-document state.

`app.py` currently sets neither organization nor application name, so `QSettings` has nothing to key on. M7.2 adds `setOrganizationName("Parrow Horrizon Studio")` and `setApplicationName("Pluton")`.

`window_state.py` owns two keys, saved on `closeEvent`:

| Key | Source |
|---|---|
| `window/geometry` | `QMainWindow.saveGeometry()` |
| `window/state` | `QMainWindow.saveState(version=WINDOW_STATE_VERSION)` — toolbar and dock positions plus visibility |

`WINDOW_STATE_VERSION` starts at `1`. When M7.3 adds its panel, bumping it cleanly discards incompatible saved layouts rather than half-restoring them.

**Every failure mode falls back to defaults, never to a broken window.** `restoreState`/`restoreGeometry` return `False` on version mismatch or corruption; those return values are checked, and the restore is additionally guarded so a malformed settings store cannot prevent startup.

`View ▸ Reset Toolbars` clears both keys and reapplies the default layout live, with no restart.

**Test isolation.** On Windows `QSettings` writes to the real registry, so every function in `window_state.py` takes the settings object as a parameter and tests inject a temporary `QSettings(tmp_path / "t.ini", QSettings.IniFormat)`. The suite touches no real user state.

## 2. Module layout

```
python/pluton/ui/
  actions.py         NEW   pure data: ActionSpec / ToolbarSpec / MenuSpec / CursorStyle /
                           context tables. Imports no Qt.
  icons.py           NEW   icon(stem) -> QIcon; palette recolor; cache; raises on miss
  cursors.py         NEW   CursorStyle bases, compose_cursor(), per-tool cache
  ui_builder.py      NEW   build_menubar / build_toolbars / build_shortcuts
  context_menu.py    NEW   context_menu_ids() (pure) + build_context_menu()
  window_state.py    NEW   save/restore/reset over an injected QSettings
  icons/*.svg        NEW   29 assets
  main_window.py     MOD   handlers only; construction delegated; ~115 lines removed
python/pluton/
  app.py             MOD   organization + application name
python/pluton/model/
  model_queries.py   NEW   select_all_ids(), model_bounds() — pure read-only model queries
python/pluton/viewport/
  camera_framing.py  NEW   frame_bounds() — pure numpy, imports no model type
```

`select_all_ids` and `model_bounds` are grouped because both are read-only walks over the model graph honouring the active context and tag visibility. `frame_bounds` is kept separate and model-free so it can be tested with plain arrays, mirroring how M7.1 moved the closest-point helpers into `geometry/ray.py` to keep a layer boundary clean.

Net effect on `main_window.py`: roughly 115 lines of menu and `QShortcut` construction move out, and the ~40 lines M7.2 would otherwise have added land in the builders. It ends the milestone smaller than it started.

## 3. Testing

**Headless (no `QApplication`)** — the registry's whole value:

- every registered tool has a toolbar action, an icon stem, and a cursor style
- no duplicate shortcut across the entire registry
- every `ActionSpec.handler` name exists on `MainWindow` (via `hasattr` on the class)
- every declared `icon` stem resolves to a real file in `ui/icons/`
- every id referenced by a toolbar, menu, or context table resolves to a declared action
- tool `ActionSpec`s match the registered `Tool` instances' `name` and `shortcut`
- `context_menu_ids` returns the specified entries for each target and flag combination
- `select_all_ids` respects the active context and tag visibility
- `model_bounds` / `frame_bounds`: a unit cube frames with margin from a known pose; view direction is preserved; empty model returns `None`; zero-extent input is clamped, not divided by

**Icon spec enforced mechanically:** a test parses all 29 SVGs with `xml.etree`, asserting `viewBox="0 0 24 24"` and that only whitelisted element tags appear. A stray `<text>`, gradient, or filter fails the suite rather than rendering differently on another Qt build.

**With `pytest-qt`:** toolbar construction (counts, titles, separator placement); tool `QActionGroup` exclusivity — arming from the toolbar leaves exactly one action checked, and keyboard activation updates the toolbar; cursor hotspots; context-menu enablement per target; a `window_state` save → restore → reset round-trip on injected temporary storage; `View ▸ Toolbars` toggles.

**Regression:** the existing 1074 pytest tests stay green; `ctest` stays **82/82** (no C++ change).

## 4. Decisions

- **D1 — Declarative action registry over imperative construction.** The alternative (per-surface builder functions) is simpler in the moment but scatters the taxonomy across function bodies, making "does every tool have an icon?" answerable only by launching the app. The registry matches the pattern the codebase already uses repeatedly — M5a's `resolve_face_pass` descriptor table, M5b's `plan_face_batches`, M7d's `plan_annotation` — where a pure planning layer is tested headlessly and a thin Qt layer applies it.
- **D2 — SketchUp-style dockable top toolbars**, not a Blender-style left tool column. Pluton's modeling paradigm is SketchUp's; M7.3's right panel is Blender-style, and the two compose fine.
- **D3 — Original SVG icon set authored in-repo**, not a third-party pack and not `QPainter` code. Text-diffable, versioned like source, individually replaceable in a vector editor without touching Python, and loaded through the `importlib.resources` pattern shaders already use.
- **D4 — Cursors derived from the icon set** by composition rather than drawn as separate art. One pipeline, no drift.
- **D5 — `cursor` on `ActionSpec`, not on the `Tool` ABC.** Keeps Qt presentation concerns out of the tool classes and avoids an eighteen-file churn.
- **D6 — Context menus expose only commands that already exist**, plus Select All and Zoom Extents. Hide/Unhide and Entity Info are withheld for M7.3, where the Outliner and Properties panel already own visibility and attributes; building them here would build them twice.
- **D7 — Window state persists, with guarded restore and a reset escape hatch.** Dockable toolbars that forget their arrangement every launch would be worse than fixed ones. The versioned `saveState` gives M7.3 a clean invalidation point.
- **D8 — Entries are disabled, not hidden, when inapplicable.** A menu whose items keep the same position is learnable; one that reflows is not.

## 5. Out of scope

- **Hide/Unhide, Entity Info, the Outliner, the Properties panel, and relocating the per-tool option bars** → M7.3. The option bars stay exactly where they are.
- **Preset camera views** (Top / Front / Iso) — not scheduled in any milestone. Zoom Extents is the only camera addition.
- **Toolbar customization UI** (adding or removing individual buttons). SketchUp has it; it is not worth building.
- **Application/window icon and splash screen.** These need a logo, which is a branding decision, not an implementation one. Named here as a known visible gap rather than silently filled.
- **Localization**, and icon theming beyond the light/dark palette recolor.
- **Loose edge/face tagging** ([#69](https://github.com/Parrow-Horrizon-Studio/pluton/issues/69)) — the reason `Assign Tag` is instance-only.

## 6. Risks

- **The 29 icons are the long pole**, and the one deliverable where correctness can be guaranteed but aesthetic quality cannot. Mitigation: one file per icon with a fixed spec, so any individual glyph can be redrawn later with no code change.
- **`QSettings` writes to the Windows registry.** Mitigation: settings are injected, never constructed inside the functions under test.
- **A saved layout could hide every toolbar**, leaving no way to get them back. Mitigation: `View ▸ Reset Toolbars` is a menu-bar action, which `restoreState` cannot hide.
- **`main_window.py` churn.** The file is being restructured while M7.3 is queued to modify it next. Mitigation: the restructure is mechanical (construction moves out, handlers stay), and the full existing suite must remain green throughout.

## 7. Sequencing

Registry and asset foundations first, so every later task consumes a tested base:

1. `actions.py` registry + invariant tests (no Qt)
2. `icons.py` loader + the 29 SVGs + spec-enforcement test
3. `cursors.py` composition + hotspot tests
4. `ui_builder.py` — menus and shortcuts rebuilt from the registry (behaviour-preserving; existing suite is the proof)
5. `ui_builder.py` — the seven toolbars + `QActionGroup` exclusivity + `View ▸ Toolbars`
6. Cursor wiring into `_activate`
7. `model_queries.py` + `camera_framing.py`, then Select All and Zoom Extents wired to them
8. `context_menu.py` + right-click wiring
9. `window_state.py` + `app.py` naming + Reset Toolbars
10. Full regression, manual visual pass, roadmap annotation, release v0.4.0
