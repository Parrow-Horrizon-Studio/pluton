# M7.5c: UV storage and texture round-trip

**Status:** design, approved in conversation 2026-09-15.
**Milestone:** M7.5c, the imported-UV half of the roadmap's "M7.5 Materials & textures".
**Predecessor:** M7.5b Textures, shipped v0.8.0.

## Context

M7.5b gave pluton textures, with one deliberate exclusion stated in its section 1.2:
**faces do not store UVs, they are projected.** A material carries a `texture_size`, a 2D
basis is built on each face's own plane in definition-local space, corners are projected
onto it, and a per-face placement composes on top. That model is SketchUp's, it pins a
texture to the geometry so a moved group carries its textures with it, and it needs no
per-corner storage anywhere.

It also cannot represent a model that arrives with baked per-corner UVs. That is the whole
of what this milestone adds. Three deferrals point here: `#80`'s OBJ `vt` and `.mtl` map
round trip, glTF `TEXCOORD_0` and texture import, and the general ability to open a
textured model authored elsewhere and have it look the way its author intended.

The starting position for imported UVs is empty in both importers. `parse_obj`
(`python/pluton/io/obj_codec.py:133`) splits each face token on `/` and keeps only the
vertex index, and `:143` records `vn`/`vt` as ignored. `_parse_mtl` (`:75`) returns
`dict[str, tuple[float, float, float]]`, `Kd` only, no `map_Kd`. The Assimp bridge
(`cpp/src/gltf_import.cpp:61-64`) reads `mNumVertices` and `mVertices` per mesh and nothing
else per vertex, never touching `mTextureCoords`, and never reads `scene->mTextures`, so
embedded images do not cross the language boundary at all.

## 1. Scope

### 1.1 What ships

A model imported from OBJ or glTF keeps the UV coordinates its author baked into it, and
the image those coordinates address. Those UVs survive the edits that can preserve them
and fall back to M7.5b's projection where they cannot. A face can be returned to the
projection deliberately, with one undoable action. Export bakes the resolved coordinates
so a model leaving pluton looks the same in the tool that opens it.

### 1.2 Storage

A new sidecar on `Scene`, keyed by `(face_id, Side)`, holding a list of `(u, v)`
**parallel to that face's boundary loop**. It sits beside the four face-keyed sidecars
`Scene` already owns (`_face_materials_front`, `_face_materials_back`,
`_face_placements_front`, `_face_placements_back`) and follows their conventions exactly.

Per corner rather than per vertex, because the kernel welds coincident vertices:
`add_vertex` is position-idempotent, so a cube's eight corners are eight vertices no matter
how many faces meet there. A UV seam requires one welded vertex to carry different
coordinates on different faces, which per-vertex storage cannot express and per-corner
storage handles by construction.

In Python rather than in the C++ `Face` struct, because `Face` has no per-corner attribute
slot today and adding one would put a kernel schema change, a nanobind signature change and
a `ctest` rewrite in front of every other piece of this milestone. The sidecar reaches the
same result with no kernel change and matches where materials and placements already live.

### 1.3 Resolution

Three steps, evaluated per face per side in `_face_uv_geometry`:

1. **Base.** Stored UVs if this face and side have them, otherwise M7.5b's plane
   projection.
2. **Placement.** The existing offset, scale and rotation applied on top, whichever base
   was used.
3. **Bake.** Into the vertex buffer as today, unchanged.

Placement composes on top of both bases rather than being replaced by stored UVs. A face
that arrives with imported coordinates is still nudgeable with the same controls as a
projected one, and the placement fields never become dead for part of a model.

This resolution is a **named pure function with two callers**, the renderer's bake and the
exporter. It is not a private step inside the renderer. See D9.

### 1.4 Edit maintenance

This is not a UV problem. It is a sidecar problem that UVs join.

`HalfEdgeMesh::split_edge` (`cpp/src/halfedge.cpp:808-833`) captures both incident loops,
calls `remove_face` on each, and rebuilds them through `add_face_from_loop`. **The faces
get new ids.** `dissolve_edge` does the same at `:773`. `SplitEdgeCommand` does not carry
the sidecars across, so splitting an edge on a painted face silently un-paints it today,
verified:

```
face 0, painted material 7
split_edge  ->  face 0 destroyed, face 1 created
face 1 material -> 0   (Default)
sidecar     -> {0: 7}  (stale entry on a dead face)
```

Building UV maintenance alone would leave UVs that survive a split while the paint under
them falls off, which is worse than either behaviour by itself. So `Scene` gains **one**
internal transfer point that every destroy-and-rebuild site routes through, and each
sidecar declares how it transfers:

- **Materials.** Copied verbatim. A face's paint does not depend on its loop.
- **Placements.** Copied verbatim. Offset, scale and rotation are scalars on the face's
  plane, and a split does not move the plane.
- **Stored UVs.** The new loop is the old one with a single vertex `w` inserted between
  `va` and `vb` (`loop_with_inserted`, already in the kernel). The transferred array is the
  old array with one entry inserted at that index, **lerped at the same `t` the split
  used.** The texture stays put across the new vertex.

Where the transfer cannot be honest, it does not guess. `dissolve_edge` merges two faces
into one, so **every** sidecar has two candidate sources and no defensible winner, not just
UVs: two unrelated parameterisations, and potentially two different materials and two
different placements. Dissolve is therefore left exactly as it behaves today, with the
merged face unpainted, unplaced and projected, for all four sidecars. Picking the first
face's values would be arbitrary, and resolving it properly is a question about merge
semantics that belongs to whatever milestone wants to answer it. The same applies to any
face born from `add_face_from_loop` with no ancestor.

`set_vertex_position` leaves the loop length unchanged and therefore leaves UVs untouched,
which correctly stretches the texture with the surface.

Repairing the material and placement transfer is a behaviour change to a shipped feature
and it lands here, because this milestone rewrites the exact code path. See D4.

### 1.5 Import

**OBJ is pure Python.** `parse_obj` keeps the `vt` index per corner, `_parse_mtl` learns
`map_Kd`, and the referenced image is resolved beside the `.obj` exactly as the `.mtl`
already is. That closes the `vt` half of `#80`.

**glTF is a C++ change.** `GltfMesh` (`python/pluton/io/gltf_scene.py:20`) and the Assimp
bridge both gain UV and image fields, extracted from `mTextureCoords[0]` with
`mNumUVComponents`, and from `scene->mTextures` for embedded images, which Assimp returns
either as compressed bytes or as raw texels depending on the source. **`ctest` moves off
104 for the first time since M7.4.**

An imported polygon's corners map onto the kernel loop positionally and in order, so the
mapping needs no matching logic. **Both sides receive the imported array**: a source format
has one UV set per corner and pluton has two, and writing both means an imported model
reads correctly from either side without import having to hold an opinion about sidedness.

Import stays best-effort, as `obj_io` already is. A face whose UV data is malformed, short
or absent drops to projection for that face alone and increments a counter, the same
degradation shape as a missing `.mtl`, never a failed import.

### 1.6 Export

Export bakes the resolved coordinates. Both exporters call the same resolver the renderer
bakes through, so what leaves pluton is what pluton drew.

**OBJ.** `ObjDocument` (`python/pluton/io/obj_codec.py:27`) holds one shared vertex pool
that faces index into, with no per-corner slot. It gains a parallel UV pool, `ObjFace`
gains per-corner `vt` indices, `write_obj` emits `f v/vt v/vt ...`, and the `.mtl` block
gains `map_Kd`. The image is written as a sibling file through the existing atomic
temp-and-replace write.

**glTF.** Each per-material primitive gains a `TEXCOORD_0` accessor, and the material gains
`baseColorTexture` with its image, sampler and texture records. Images embed in the buffer
for `.glb` and write as siblings for `.gltf`, matching how each container already handles
geometry.

**Export stays front-only.** Both exporters already call `mesh.face_material(f.id)` with
the default side (`obj_io.py:60`, `gltf_export.py:45`), so a face's back material has never
been exported. Neither format has a second UV set or a second material per face. Exporting
the front side's resolved UVs alongside the front material is the only self-consistent
choice, and it turns an existing silent limitation into a documented one.

A round trip has a consequence worth stating: export a model and re-import it and those
faces return with **stored** UVs where they previously had none, so they no longer
re-project when the group moves. That is correct for a baked export, and it is the clearest
argument for `Reset to projection` being a first-class action.

### 1.7 Persistence

Schema 6 to 7, additive. Two new keys, `face_uvs` and `face_uvs_back`, each mapping a
face-index string to a flat list of floats, two per loop corner.

Keyed by **face index in enumeration order**, not face id, because save compacts id gaps
(`python/pluton/io/document_codec.py:47-58`). Sparse in the same way placements already
are: an array is written only when the face actually has one, so a document built entirely
inside pluton gains two empty dicts and nothing else.

Load validates one invariant: the array length must be exactly twice the loop length. A
mismatch raises `PlutonFormatError`, matching how `geometry_from_dict` already treats a bad
vertex index. This is the one place where dropping to projection would be wrong. A
`.pluton` file is ours, so a malformed one is corruption to report, not damage to paper
over. Import is the lenient path, open is not.

The version gate at `pluton_file.py:73` accepts equal-or-older and rejects newer, so v0.8.0
files open unchanged through `.get("face_uvs", {})` with no migration code.

### 1.8 Reset to projection

A button in the placement group that already exists
(`python/pluton/ui/properties_dock.py:135`), under the same enable rule, backed by a new
undoable command.

**It clears stored UVs only and leaves the placement alone.** Projection is the base and
placement is a separate layer on top, per 1.3. A control labelled "reset to projection"
that also zeroed an offset and rotation would be doing two things under one name, and the
placement fields are already directly editable back to their defaults.

**Its enabled state is the only indicator that a face carries stored UVs.** Disabled means
the face follows the projection, enabled means it has its own coordinates. Without this, an
imported face and a projected face are indistinguishable until the group moves and one of
them slides.

## 3. Testing

Four tests carry the milestone, and each must fail against a specific wrong implementation
rather than merely pass against the right one.

**Material loss on split.** The reproduction in 1.4 fails against `main` today. That is
what makes it worth writing.

**UV interpolation at the split point.** Split at `t = 0.25`, and the inserted corner's UV
must equal `lerp(uv_a, uv_b, 0.25)`. This discriminates against copying a neighbour's UV
and against hardcoding the midpoint, both of which pass any test that splits at 0.5. **No
test in this milestone may split an edge at 0.5.**

**Seam preservation.** Import a cube whose layout puts a seam on a shared edge, then assert
one welded kernel vertex carries different UVs on its two faces. This fails if the storage
is ever "simplified" to per-vertex.

**Renderer and exporter agree.** A round trip can pass while both sides are wrong the same
way, so it is not sufficient alone. The discriminating test compares the exporter's output
for a face against `_face_uv_geometry`'s baked buffer for that same face, with a placement
applied so all three resolution steps are exercised.

A **manual visual verification pass** closes the milestone, on an image asymmetric under
every rotation and mirror. The fixture trap specific to this milestone: a unit quad in the
XY plane with UVs spanning 0 to 1 is very close to what the projection already produces, so
it would pass whether or not the stored UVs were read at all. The fixture must be a model
where stored UVs and the projection differ visibly.

## 4. Decisions

**D1.** Stored per-corner UVs live in a Python sidecar on `Scene` keyed `(face_id, Side)`,
not in the C++ `Face` struct. Rationale in 1.2.

**D2.** Resolution is base, then placement, then bake. Placement composes on top of stored
UVs rather than being replaced by them.

**D3.** UVs survive edits where they can. One shared transfer point serves every face-keyed
sidecar rather than four parallel mechanisms.

**D4.** The material and placement transfer repair lands in this milestone, not as a
separate issue, because this milestone rewrites the code path that breaks them.

**D4a.** `dissolve_edge` is unchanged for all four sidecars. A merge has two candidate
sources and no defensible winner, which is a question about merge semantics rather than
about UVs. The merged face is unpainted, unplaced and projected, as it is today.

**D5.** Stale sidecar entries on dead faces are left alone. Face ids are never reused
(`faces_.push_back`, no free list), so an orphan can never be misattributed, and not
clearing on `remove_face` is what makes undo of a delete restore the paint for free. The
leak is bounded and cosmetic; a purge would have to be undo-aware for no gain.

**D6.** Import writes the source's single UV array to both sides.

**D7.** `pluton/io` stays Qt-free. The image decoder is injected into the import command by
the UI, with tests passing a stub. `has_transparency` is scanned from decoded pixels, and
that scan lives at the UI edge today (`ui/materials_page.py:464`); import has no UI edge,
and injection is what keeps the codec tests free of a `QApplication`.

**D8.** Export bakes the projection, front side only.

**D9.** One resolver, two callers. Renderer and exporter must not hold separate
implementations; the failure mode is a model that looks right in pluton and wrong
everywhere else.

**D10.** Schema 7 is additive and sparse, keyed by face index. A UV array of the wrong
length raises rather than degrading.

**D11.** `Reset to projection` clears stored UVs only, never the placement.

**D12.** The reset control's enabled state is the stored-UV indicator. No separate badge.

**D13.** `vn` is out of scope. `#80` closes on its `vt` half and `vn` gets its own issue.

## 5. Out of scope

- **`vn` import and export.** D13. Normals are a separate concern from coordinates and
  pluton computes face normals itself.
- **`#112`, the model-global bake gate.** It touches the exact bake loop this milestone
  reopens, which is the argument both for and against folding it in. Kept out: folding an
  optimisation into a feature milestone is how M7.5b's perf regression happened.
- **`#111`, texture purge and delete UI.** Unrelated to coordinates.
- **A right-click entry for Reset to projection.** It needs a registry action and a decision
  about which of M7.2's five context menus owns it. The button covers the need.
- **Multiple UV sets per face beyond front and back.** `TEXCOORD_1` and up are read past.

## 6. Risks

**The Assimp bridge is the riskiest piece and the only C++.** Embedded images arrive either
as compressed bytes or as raw texels depending on the source, and both shapes must be
handled. Every C++ brief in this milestone carries **all three lint gates**: `ruff check`,
`ruff format --check`, and `clang-format --dry-run --Werror` pinned to 18.1.8. Omitting the
third turned `main` red during M7.5b's close-out. Draco-compressed meshes carry UVs too, so
the existing permanent Draco CI gate needs a UV-bearing asset or it will keep passing while
UV extraction silently breaks.

**Performance, on a path with a known history.** M7.5b's naive per-face bake was 15.7 times
slower before vectorisation, and the cost was the per-face Python loop rather than the
arithmetic. Stored UVs introduce a per-face branch into that exact loop, and the obvious
implementation de-vectorises it. The measurement method exists: the `_upload_definition`
minimum on a 9,600-face definition. A number before and after, not an assurance.

**Breadth.** This cuts kernel C++, `io`, `scene`, renderer, UI and persistence, which is
wider than M7.5b. Sequencing in section 7 exists to make it stoppable at coherent points.

## 7. Sequencing

Storage, maintenance, persistence and the UI first, landing a complete and verifiable
feature with no importer involved: the sidecar, the shared transfer point and the
`SplitEdgeCommand` repair, the resolver, schema 7, then `Reset to projection`. Then OBJ,
which is pure Python and closes `#80`'s `vt` half end to end including export. Then glTF,
which is the only C++ and the only `ctest` movement.

Each of the three is independently shippable. If glTF proves larger than it looks, the
milestone stops at a coherent point rather than mid-flight.

D16: export UVs are all-or-nothing per primitive, since a material group's `is_textured` is uniform but its `has_stored_uvs` is not, and a partial accessor is invalid glTF; a group that needs UVs at all gets every face's resolved UVs, with projection standing in for a face that has nothing stored. D16 widens a consequence stage 2 already found and accepted for OBJ: round-tripping a face with stored UVs freezes its live projection, since a re-import reads back stored coordinates instead of reprojecting. OBJ freezes only the one face, because `f v/vt` indexes two pools independently and a face with nothing stored simply carries no `vt`. glTF cannot do that: lifting the gate from per-face to per-primitive means a glTF round trip of a model where ONE face in a material group has stored UVs now freezes the projection of EVERY face in that group, stored or not, because the primitive's TEXCOORD_0 accessor is one array with no per-face opt-out. The decision is still correct, since a partial accessor is not valid glTF and there is no other honest choice, but the widening was not on the record until now. D17: an embedded image that Assimp reports as raw texels rather than an encoded blob is skipped and counted rather than encoded, because encoding it would put a codec inside `pluton/io`, which stays Qt-free by design. D18: `baseColorFactor` is kept alongside `baseColorTexture`, matching the multiply semantics OBJ's `Kd` plus `map_Kd` already has, so the two exporters agree on what a material's own colour does to its texture. An undocumented deviation from section 1.6, caught in the whole-branch review: that section binds this stage and says the material gains "baseColorTexture with its image, sampler and texture records," but `GltfAsset.add_texture` writes no sampler, and a test pins its absence. The choice is correct and stands: an absent sampler defaults to REPEAT wrapping and automatic filtering per the glTF 2.0 spec, which is exactly what Pluton's projected UVs need when they run outside 0..1, and writing an explicit sampler object would be JSON that changes nothing a consumer does with the texture. Sidecar image filenames now have the texture's own unique id appended to the sanitized name, so two distinct textures can never collide on a shared filename and silently overwrite one another regardless of what either is named; this is the same bug family as `#119`, filed against the OBJ exporter, where two materials whose names sanitize alike merge on write and one material and its image vanish from the output entirely, and glTF export ships with the fix built in rather than inheriting it. `ctest` moved to 121 from the 116 baseline, the first movement since M7.4, all of it landing in Task 2's Draco decode and UV accessor coverage; nothing after Task 2 touched C++.
