# M7.5a: Materials

**Status:** design, approved in conversation 2026-09-08.
**Milestone:** M7.5a, the materials half of the roadmap's "M7.5 Materials & textures".
**Predecessor:** M7.4 Geometry tools, shipped v0.6.0.

## Context

M5b gave pluton a material system sized for its moment: `Material(id, name, color)`, a
solid opaque RGB triple, one material per face, a per-model `MaterialLibrary` seeded with
a Default plus eight builtins, and a Paint tool that assigns one face per click. M7.3
folded the Materials dock into the Properties panel as a tab. Nothing since has touched
the model.

Five issues have accumulated against it, all deferred with a named milestone:
`#65` drag-to-paint, `#66` material editing, rename and delete with re-propagation,
`#67` per-side face materials, `#68` translucent materials, and `#71` per-tag colour with
a Color-by-Tag view mode. The roadmap adds a sixth requirement in prose: a "PBR-shaped
material model" that "lays the foundation the M12 renderer consumes".

The roadmap's M7.5 also covers UV mapping and textures. That half is deliberately split
out as M7.5b, because it cuts the same layers again for a different reason and because
translucency's draw-order decision deserves undivided attention: M12's renderer inherits
it.

The viewport renders Blinn-Phong today, with backface culling globally disabled and a
single material uniform set. Two facts about that pipeline shape this design. First, face
triangles are already grouped into contiguous per-material batches by a pure function,
`plan_face_batches`, which returns a permutation of the vertex order. Second, the fragment
shader never flips the normal for a back-facing fragment, so back faces are mis-lit today.
The first fact makes this milestone cheaper than it looks. The second is a bug this
milestone fixes as a side effect of doing per-side work properly.

## 1. Scope

### 1.1 What ships

- A PBR-shaped `Material`: base colour, alpha, metallic, roughness.
- A Phong approximation of those parameters, so metallic and roughness visibly do
  something rather than being stored and ignored.
- Per-side face materials, with a distinct default back colour so reversed faces are
  obvious at a glance.
- Translucent materials, with a two-pass draw and a per-face back-to-front sort.
- Material editing, adding and deletion, all undoable, with deletion reassigning affected
  faces to Default in one step.
- Drag-to-paint, one stroke being one undo step.
- Per-tag colour and a Color-by-Tag view mode.
- `.pluton` schema 4 to 5, additive, so v0.6.0 files still open.
- Two debt items from `#106`, listed in 1.8.

### 1.2 The material model

`Material` stays a frozen dataclass and gains three fields:

```python
@dataclass(frozen=True, slots=True)
class Material:
    id: int
    name: str
    base_color: tuple[float, float, float]
    alpha: float = 1.0        # 0..1, 1.0 opaque
    metallic: float = 0.0     # 0..1
    roughness: float = 0.5    # 0..1
```

`color` is renamed `base_color` to make the PBR shape explicit. The rename is mechanical:
`materials_page`, `paint_tool`, `scene_renderer` and the two importers are the only
readers, and both importers pass positionally through `add_custom(name, color)`, so they
need no change at all.

A material is **translucent** when `alpha < 1.0`. That single predicate drives the render
partition in 1.5.

### 1.3 The Phong approximation

The mapping lives entirely in `phong_material_for` in `render_style.py`, which is already
pure and headlessly testable. Given a `Material` it returns the existing `PhongMaterial`:

- `diffuse = base_color * (1 - metallic)`, because metals have no diffuse lobe.
- `specular = mix(vec3(0.04), base_color, metallic)`, 0.04 being the standard dielectric
  normal-incidence reflectance, and metals taking their tint from the base colour.
- `shininess = clamp(2 / roughness**4 - 2, 1, 256)`, the standard Blinn-Phong to
  roughness equivalence.
- `ambient = base_color * _AMBIENT_FACTOR * (1 - metallic)`. Ambient already tracks the
  base colour through `_AMBIENT_FACTOR`; the only change is folding in the metallic term.

Note that `phong_material_for` is not the whole story today: unpainted faces bypass it and
use `_DEFAULT_MATERIAL`, whose terms are hand-tuned rather than derived. Per-side work
means the back default needs the same treatment, so a second hand-tuned constant sits
beside it for the back Default colour. Both are constants rather than library entries, per
D3.

This is an approximation and the spec says so plainly. It will not match M12's real PBR
pixel for pixel. What it buys is that every field a user can edit changes what they see,
and that files written now already carry what M12 needs, so there is one schema migration
across the pair rather than two.

### 1.4 Per-side materials

Every face has a front and a back, defined by its normal. The two sides carry independent
material slots.

`Scene` gains `_face_materials_back` beside the existing `_face_materials`, which is
renamed `_face_materials_front`. The public accessor keeps working for every existing
caller:

```python
class Side(Enum):
    FRONT = 0
    BACK = 1

def face_material(self, f_id: int, side: Side = Side.FRONT) -> int
def set_face_material(self, f_id: int, mid: int, side: Side = Side.FRONT) -> None
def face_triangle_materials(self, side: Side = Side.FRONT) -> np.ndarray
```

`Side` lives in the scene layer, not beside `Material`. `model` imports `scene`, so the
reverse import is not available.

Material id 0, "Default", stays a single library entry but **resolves to two colours**:
the existing warm grey `(0.65, 0.65, 0.70)` on the front, and a cooler blue-grey
`(0.45, 0.50, 0.58)` on the back. The back default is a renderer constant, not a library
entry, so the swatch list stays honest while reversed faces become visible. This is
SketchUp's behaviour and the reason for it.

Painting applies to the side the user clicked, resolved by the dot product of the pick ray
against `Scene.face_normal(f_id)`, which already exists.

### 1.5 Translucency and draw order

Faces draw in two passes:

1. **Opaque**, depth writes on, as today.
2. **Translucent**, depth test on, depth writes off, sorted back to front by face centroid
   distance from the camera.

A face is translucent when **either** of its sides is. That is slightly conservative and
avoids splitting one face across two passes.

`plan_face_batches` gains the pair key and the partition. It stable-sorts triangles by
`(is_translucent, front_mid, back_mid)`. Because `is_translucent` leads the key,
translucent triangles land as a **contiguous suffix** of the reordered vertex order. That
property is what makes the re-sort cheap, and it is the single most important invariant in
this milestone's render path.

```python
@dataclass(frozen=True)
class FaceBatch:
    front_material_id: int
    back_material_id: int
    first: int
    count: int

@dataclass(frozen=True)
class BatchPlan:
    vertex_order: np.ndarray     # permutation, as today
    opaque: list[FaceBatch]
    translucent: list[FaceBatch]

def plan_face_batches(
    front_ids, back_ids, translucent_mids: set[int]
) -> BatchPlan
```

The translucent suffix is re-permuted by centroid distance and its vertex slice
re-uploaded when the camera moves or the scene changes. A static view costs nothing. Cost
scales with translucent face count rather than scene size, which in a modeller means the
windows.

If that ever proves too expensive, the optimisation is an index buffer covering the
translucent range, so a re-sort rewrites three `uint32`s per triangle instead of the
interleaved vertex data. **That optimisation is explicitly not built now.**

Interpenetrating translucent faces will still render incorrectly. No sort can fix that;
order-independent transparency can, and it belongs to M12 because it needs multiple float
render targets the current pipeline does not have.

### 1.6 The shader

`phong.frag` gains a second material uniform set, suffixed `_back`, and selects between
the two with `gl_FrontFacing`. Separately and independently, it flips the normal for
back-facing fragments:

```glsl
bool front = gl_FrontFacing;
vec3 N = normalize(v_world_normal);
if (!front) N = -N;
```

The flip is a bug fix, not a feature. With culling disabled and one uniform set, today's
back-facing fragments shade against a normal pointing away from the viewer.

### 1.7 Material editing, adding and deletion

Editing a material's colour re-propagates to every face using it for free, because faces
reference materials by id and the renderer reads uniforms from the library per batch at
draw time. **A colour edit therefore needs no re-batch.** An alpha edit can move a
material across the opaque/translucent boundary and **does** force one. That asymmetry is
easy to miss and is called out here so it gets a test.

Deleting a material that faces are painted with removes it and repaints every affected
`(face, side)` to Default, as one undoable command. The confirmation names the count
first: "Delete Brick Red? It is painted on 14 faces." Built-ins are ordinary entries and
may be edited or deleted. Only Default (id 0) is protected, because it is the fallback
every unpainted side resolves to.

Adding a material from the UI is **not undoable today**: `MaterialsPage` calls
`MaterialLibrary.add_custom` directly. That becomes visible the moment deletion is
undoable, so this milestone closes it.

Rename is an edit of the `name` field, so there is no separate rename command.

### 1.8 Debt from `#106`

Two items, chosen because both are small and neither touches the material system:

- **The primitive footprint preview and commit disagree about their plane.** The stage-one
  rubber band draws at world `z = 0` while `_commit_footprint` pins local `z = 0`, so
  inside a group translated in z the rectangle drawn and the primitive placed sit on
  different planes. `RectangleTool` uses the opposite convention, so the two tools also
  disagree with each other. This is a genuine user-visible bug.
- **A public `vertex_id` accessor on `AddVertexCommand`**, retiring the three private
  `_vertex_id` reach-ins in `sweep_support`, `mesh_builder` and `push_pull_tool`. The
  M7.4 final reviewer asked for this explicitly.

### 1.9 Per-tag colour and Color-by-Tag

`Tag` gains a `color`, editable via a swatch in the Tags page. New tags are seeded by
cycling a fixed palette of visually distinct hues, so two tags created in a row never
share a colour. The palette is separate from the material builtins, because tag colours
exist to be told apart rather than to look like materials.

Color-by-Tag is orthogonal to the four face styles, so it joins `RenderStyle` beside
`xray` rather than becoming a fifth `FaceStyle`. When on, the resolved diffuse comes from
the owning instance's tag colour and materials are bypassed entirely. Bypassing is the
point of the mode and keeps it from entangling with per-side resolution.

## 3. Testing

The milestone is fortunate in that its hardest logic is pure and headless:
`phong_material_for`, `plan_face_batches` and the translucent sort all test without a
`QApplication` or a GL context.

Traps to write against explicitly, each of which has produced a non-discriminating test in
an earlier milestone here:

- A paint test asserting only "the face changed" passes against a tool that ignores side.
  Front and back must be asserted as distinct slots, from cameras on both sides.
- A stroke test asserting "one undo step" passes trivially on a one-face fixture. Use a
  fixture where a broken implementation yields more than one.
- A batching test asserting only "batches exist" misses the whole design. Assert the
  **translucent-suffix property** directly.
- A delete test that checks the material is gone but not the faces misses the reassignment
  half. Assert both, and assert undo restores both.
- The re-batch asymmetry from 1.7 needs its own pair of tests: editing a colour must not
  invalidate the batch plan, and editing alpha across the 1.0 boundary must. A test that
  re-batches unconditionally passes both halves and proves nothing.
- A PBR mapping test on `metallic = 0, roughness = 0.5` cannot distinguish the mapping from
  a constant. Use values that move each output term independently.

The shader change resists unit testing. It gets a manual visual verification pass at
release, which M7.4 demonstrated is where this class of defect actually surfaces: that
pass found a preview defect none of 1800 tests caught.

Migration gets a fixture: a v0.6.0 `.pluton` file loaded and asserted for the schema-4
defaults.

## 4. Decisions

- **D1.** Material carries full PBR fields now, approximated by Phong, rather than alpha
  only. One schema migration across M7.5a and M7.5b instead of two, and the roadmap's
  "foundation" promise is kept.
- **D2.** Per-side materials follow SketchUp: independent slots, painting hits the clicked
  side, and an unpainted back renders in a distinct default colour.
- **D3.** The back default is a renderer constant, not a library entry, so it never appears
  as a swatch.
- **D4.** Translucency sorts per face, not per batch. Per batch is cheaper and wrong in the
  common case, because every window in a building shares one glass material.
- **D5.** A face is translucent if either side is.
- **D6.** Order-independent transparency is deferred to M12.
- **D7.** Batches key on the `(front, back)` pair, and the shader branches on
  `gl_FrontFacing`. The alternative, two culled passes, needs no shader change but forces
  four passes and sorts each side of a translucent face independently.
- **D8.** Deleting an in-use material reassigns its faces to Default in one undoable step.
  Built-ins are deletable; only Default is protected.
- **D9.** Rename is an edit, not its own command.
- **D10.** Color-by-Tag is a `RenderStyle` flag beside `xray`, not a fifth `FaceStyle`, and
  bypasses materials entirely.
- **D11.** `Material.color` is renamed `base_color`.

## 5. Out of scope

UV mapping, texture assets, texture sampling in the shader, the OBJ `.mtl` and `vt`
round-trip (`#80`), and thumbnails or textures in the `.pluton` container (`#78`). All
M7.5b.

Order-independent transparency, and any real PBR shading model. M12.

The remaining `#106` items beyond the two named in 1.8.

## 6. Risks

- **The two-sided batch key multiplies batch count.** In practice most faces share one
  pair, so the count stays near today's. A pathological model that paints every face's back
  differently would not. Accepted: batch count is bounded by distinct pairs actually used,
  and a modeller's palette is small.
- **The translucent re-sort runs during orbit.** Cost is proportional to translucent faces
  only, but a scene that is mostly glass would pay it every frame. The index-buffer
  optimisation is the escape hatch and is deliberately not built until measured.
- **The Phong approximation will not match M12.** Files are forward-compatible; the pixels
  are not. Stated in the UI is out of scope, but the spec records the expectation.
- **`scene_renderer.py` is already the largest file in the viewport package** and this
  milestone adds a second pass to it. If it grows unwieldy, the pass structure is the
  natural split, not the material handling.

## 7. Sequencing

1. `Material` PBR fields and the Phong mapping. Pure, headless, no UI.
2. `Side`, two-sided `Scene` storage and accessors.
3. `plan_face_batches` pair key and translucent partition. Pure, headless.
4. The translucent sort.
5. Renderer two passes, shader uniforms and the normal flip.
6. Material commands: add, edit, delete.
7. The Materials page editor.
8. Paint tool side resolution and the drag stroke.
9. `Tag.color`, the Tags page swatch, Color-by-Tag.
10. Schema 4 to 5 and the migration.
11. The two `#106` debt items.
12. Regression, docs, release.

Steps 1 through 5 are the load-bearing spine and land before any UI depends on them.
Step 3's suffix invariant gates step 4, and step 5 gates the visual pass.
