# M7.5c Stage 2: OBJ UV and texture round-trip, Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Import a textured OBJ with its baked per-corner UVs and its `map_Kd` image, and export one back out with the projection baked in.

**Architecture:** `parse_obj` stops discarding the `vt` index it already reads and `_parse_mtl` learns `map_Kd`, so `ObjDocument` carries UV coordinates and a per-material image filename. `obj_io` resolves those filenames beside the `.obj`, reads the bytes, and passes them through an **injected decoder** so `pluton/io` stays Qt-free. Imported UVs land in the `(face_id, Side)` sidecar stage 1 built, written to both sides. Export resolves each face's UVs through a new shared per-face resolver pinned by equivalence test to the renderer's batched path.

**Tech Stack:** Python 3.13, numpy, pytest, PySide6 (UI task only). No C++, so `ctest` stays at 116.

**Spec:** `docs/2026-09-15-M7.5c-uv-storage-design.md`

**Predecessor:** stage 1, `docs/2026-09-15-M7.5c-1-storage-plan.md`, shipped in commits `57fe9b1` through `9532d2f`.

**Why the return type changes rather than a second function:** a single pass over the MTL text already tracks `current`, and two passes would have to duplicate the `newmtl` state machine. The one caller is `parse_obj`.

**Handle these real-world MTL forms.** `map_Kd` lines carry optional arguments before the filename, and filenames can contain spaces:

```
map_Kd brick.png
map_Kd textures/brick.png
map_Kd -s 1 1 1 brick.png
map_Kd my brick.png
```

Take the filename as **everything after the last argument-looking token**. An argument token starts with `-` and is followed by its own values, so the simplest correct rule that covers the common cases is: drop a leading run of tokens where a token starting with `-` consumes itself and every following numeric token, then join the remainder with spaces.

```python
def _map_kd_filename(parts: list[str]) -> str | None:
    """The filename from a `map_Kd` line, skipping its option arguments.

    OBJ map lines may carry options before the filename (`-s 1 1 1 brick.png`)
    and filenames may contain spaces (`my brick.png`), so neither parts[1] nor
    parts[-1] is right on its own. Drop a leading run of option tokens, each
    consuming itself and any numeric values that follow it, then join what is
    left.
    """
    i = 1
    while i < len(parts) and parts[i].startswith("-"):
        i += 1
        while i < len(parts):
            try:
                float(parts[i])
            except ValueError:
                break
            i += 1
    name = " ".join(parts[i:]).strip()
    return name or None


def _parse_mtl(mtl_text: str) -> tuple[dict[str, tuple[float, float, float]], dict[str, str]]:
    """Parse an MTL to (name -> Kd colour, name -> map_Kd filename)."""
    materials: dict[str, tuple[float, float, float]] = {}
    textures: dict[str, str] = {}
    current: str | None = None
    for raw in mtl_text.splitlines():
        line = raw.strip()
        if not line or line.startswith("#"):
            continue
        parts = line.split()
        if parts[0] == "newmtl":
            current = " ".join(parts[1:]) if len(parts) > 1 else "material"
            materials.setdefault(current, (0.8, 0.8, 0.8))
        elif parts[0] == "Kd" and current is not None:
            try:
                materials[current] = (float(parts[1]), float(parts[2]), float(parts[3]))
            except (IndexError, ValueError):
                pass  # keep the default grey
        elif parts[0] == "map_Kd" and current is not None:
            name = _map_kd_filename(parts)
            if name is not None:
                textures[current] = name
    return materials, textures
```

## Task 2: Keep the `vt` index when parsing faces

**Files:**
- Modify: `python/pluton/io/obj_codec.py` (`ObjFace` at `:17`, `ObjDocument` at `:27`, `parse_obj`'s `v` and `f` handling)
- Test: `tests/test_obj_uv_parse.py` (append)

**Interfaces:**
- Consumes: Task 1's `material_textures` field (untouched here).
- Produces: `ObjDocument.uvs: tuple[tuple[float, float], ...]`, the file's `vt` pool in order; `ObjFace.uv_indices: tuple[int, ...] | None`, 0-based indices into that pool, one per corner, parallel to `vertex_indices`, or `None` when this face carried no `vt` data.

**The exact line to change.** `parse_obj`'s face handling currently does `vtok = token.split("/")[0]` and throws the rest away. An OBJ face token is `v`, `v/vt`, `v//vn`, or `v/vt/vn`. The `vt` field is the second, and `v//vn` has it empty.

**Index conventions, which OBJ makes easy to get wrong:** indices are 1-based, and a **negative** index is relative to the end of the pool so far (`-1` is the most recently declared element). The existing vertex handling already does this: `vi = len(vertices) + vi if vi < 0 else vi - 1`. Apply the identical rule to `vt`.

**Partial data is all-or-nothing per face.** If any corner of a face lacks a `vt`, that face's `uv_indices` is `None`. A face with UVs on some corners and not others cannot produce a valid array parallel to its loop, and guessing would be worse than projecting.

```python
def read_obj_texture_bytes(path, doc) -> dict[str, bytes]:
    """Material name to image bytes, for every `map_Kd` resolvable beside the .obj.

    Best-effort in the same shape as the .mtl sibling lookup: an image that is
    missing, unreadable or outside the document's directory is skipped rather
    than failing the import. The caller decides what to do with an empty result.
    """
    base = Path(path).parent
    out: dict[str, bytes] = {}
    for name, rel in doc.material_textures.items():
        try:
            candidate = (base / rel).resolve()
            if not candidate.is_file():
                continue
            out[name] = candidate.read_bytes()
        except (OSError, ValueError):
            continue
    return out
```

```python
def _ensure_materials(materials, model, texture_bytes=None, decoder=None) -> dict:
    """Add each OBJ material to the library, reusing an existing one when name AND
    color already match. Returns name -> material_id.

    When `texture_bytes` and `decoder` are both given, each material with image
    bytes gains a Texture in the model's library and points at it. Following the
    same rule as material adds, texture adds are NOT undone by ImportObjCommand:
    no library add is undoable anywhere in pluton.
    """
    name_to_id: dict[str, int] = {}
    existing = {m.name: m for m in model.materials.materials()}
    for name, color in materials.items():
        m = existing.get(name)
        if m is not None and tuple(m.base_color) == tuple(color):
            name_to_id[name] = m.id
        else:
            new = model.materials.add_custom(name, color)
            name_to_id[name] = new.id
            existing[new.name] = new

    if not texture_bytes or decoder is None:
        return name_to_id

    for name, data in texture_bytes.items():
        mid = name_to_id.get(name)
        if mid is None:
            continue
        decoded = decoder(data)
        if decoded is None:
            continue  # unreadable image: the material stays untextured
        image_format, width, height, has_transparency = decoded
        tex = model.textures.add(name, data, image_format, width, height, has_transparency)
        model.materials.edit(mid, texture_id=tex.id)
    return name_to_id
```

```python
def _add_faces(mesh, faces, localmap, name_to_id, uv_pool=()) -> tuple[int, int]:
    """Best-effort: build each face, skipping+counting any the kernel rejects
    or any that references an unknown/out-of-range vertex index.

    Imported per-corner UVs are stored on BOTH sides (spec D6): the source has
    one set and pluton has two, so writing both means the model reads correctly
    from either side. The mapping is positional, because add_face_from_loop
    stores the loop in the order it was given.
    """
    imported = skipped = 0
    for face in faces:
        try:
            loop = [localmap[gi] for gi in face.vertex_indices]
            if len(set(loop)) < 3:  # degenerate: < 3 unique verts
                skipped += 1
                continue
            fid = mesh.add_face_from_loop(loop)
        except (KeyError, ValueError, IndexError, RuntimeError):
            skipped += 1
            continue
        if face.material is not None:
            mid = name_to_id.get(face.material)
            if mid is not None:
                mesh.set_face_material(fid, mid)
        if face.uv_indices is not None and uv_pool:
            try:
                corner_uvs = [uv_pool[t] for t in face.uv_indices]
                for side in (Side.FRONT, Side.BACK):
                    mesh.set_face_uvs(fid, corner_uvs, side)
            except (IndexError, ValueError):
                # A UV problem never costs the face: it falls back to the
                # plane projection, which is what an untextured face uses.
                pass
        imported += 1
    return imported, skipped
```

## Task 6: The shared per-face UV resolver

**Files:**
- Create: `python/pluton/viewport/uv_resolve.py`
- Test: `tests/test_uv_resolve.py`

**Interfaces:**
- Consumes: stage 1's `Scene.face_uvs`; `uv_projection.project_corners` and `apply_placement`.
- Produces: `resolve_face_uvs(scene, materials, face_id, side=Side.FRONT) -> np.ndarray`, an `(L, 2)` float32 array of resolved UVs in the face's **loop** order.

**Why this exists, and why it is not simply reused by the renderer.** Spec D9 says one resolver, two callers, because a renderer and an exporter holding separate implementations produce a model that looks right in pluton and wrong everywhere else. But the two callers need different shapes: the exporter wants per **loop** corner, once per face at export time; the renderer wants per **triangle** corner, vectorised across every face on every buffer upload. Calling a per-face function from the renderer is exactly what made M7.5b's upload 15.7 times slower.

**The resolution is therefore to pin them, not to merge them.** `uv_projection.py` already does this: its scalar functions are the reference implementation and its batched siblings are held to them by an equivalence test. This task adds the per-face reference; step 5 adds the equivalence test that fails if the renderer's batched path ever drifts from it. That is D9's actual requirement, which is that the two cannot silently disagree.

**Resolution order, from spec section 1.3:** base (stored UVs if this face and side have them, otherwise the plane projection), then placement (offset, scale, rotation applied on top of whichever base), then the caller bakes.

```python
"""One face's texture coordinates, resolved in loop order.

Spec decision D9 requires the renderer and the exporter to agree about what a
face's UVs are. They cannot share one function: the renderer needs per triangle
corner, vectorised across a whole definition on every buffer upload, and calling
a per-face routine there made M7.5b's upload 15.7 times slower. So this module
is the per-face REFERENCE implementation, and tests/test_uv_resolve.py pins the
renderer's batched path to it corner for corner. Change one and you must change
the other, exactly as uv_projection.py's scalar and batched siblings already
work.
"""

from __future__ import annotations

import numpy as np

from pluton.scene.scene import Side
from pluton.viewport.uv_projection import apply_placement, project_corners


def resolve_face_uvs(scene, materials, face_id: int, side: Side = Side.FRONT) -> np.ndarray:
    """(L, 2) float32 UVs for one face and side, in its boundary loop's order.

    Base, then placement, per spec section 1.3: stored UVs when this face and
    side have them, otherwise the plane projection at the material's real-world
    texture_size, with the face's offset, scale and rotation applied on top of
    whichever base was used.

    `materials` may be None, in which case a unit texture size is assumed. That
    matches build_face_uvs, whose `model` argument is read with getattr.
    """
    loop = scene.face_loop(int(face_id))
    stored = scene.face_uvs(int(face_id), side)

    if stored is not None:
        base = np.asarray(stored, dtype=np.float64).reshape(-1, 2)
    else:
        positions = np.array(
            [scene.vertex(v).position for v in loop],
            dtype=np.float64,
        ).reshape(-1, 3)
        size = (1.0, 1.0)
        if materials is not None:
            size = materials.get(scene.face_material(int(face_id), side)).texture_size
        base = project_corners(
            positions,
            scene.face_normal(int(face_id)),
            scene.face_center(int(face_id)),
            size,
        )

    p = scene.face_placement(int(face_id), side)
    return apply_placement(base, p.offset_u, p.offset_v, p.scale, p.rotation).astype(np.float32)
```

**One thing to check before you trust this.** The renderer takes its plane basis from the triangle buffer's normals block, NOT from `Scene.face_normal`, and `scene_renderer.py` carries a long comment saying why. `face_normal` uses Newell's method since issue `#110` and raises only on a genuinely zero-area face, so it is safe here where we are not on the render hot path. But if `test_it_agrees_with_the_renderer_for_a_projected_face_too` fails, the two normals differ and that is the first place to look. Report it rather than loosening the tolerance.

```python
        self._fid = int(face_id)
        self._side = side
        self._before = None

    def do(self, scene) -> None:
        self._before = scene.face_uvs(self._fid, self._side)
        scene.clear_face_uvs(self._fid, self._side)

    def undo(self, scene) -> None:
        if self._before is not None:
            scene.set_face_uvs(self._fid, self._before, self._side)
```

## Task 9: Visual verification pass

**Files:**
- Create: `tests/data/uv_checker.png` (a generated fixture, committed)
- Create: a throwaway render script in the scratchpad, not committed
- Modify: `docs/2026-09-15-M7.5c-uv-storage-design.md` (section 8 history)

**Interfaces:**
- Consumes: everything in tasks 1 through 8.
- Produces: rendered PNGs for a human to look at, and a history row.

**This is a gate, not a formality.** A manual render-and-look pass has caught a shipping defect the full test suite missed in **three consecutive** renderer milestones: M7.4's broken primitive preview, M7.5a's face-winding bug latent since `208384e`, and M7.5b's textures all rendering vertically mirrored past 2211 passing tests. Stage 1 could not run this gate because nothing could create a stored UV array. Stage 2 can, so it must.

**The fixture must be asymmetric under every rotation and every mirror.** M7.5b's mirrored-texture bug survived because every existing fixture was symmetric under a vertical flip. Build an image with four differently coloured borders, a letter or digit, and an off-centre mark, so any flip, rotation or transposition is instantly visible.

**Two traps recorded from M7.5b, which apply again:**
- The world axes are themselves a red horizontal and a blue vertical line, so a fixture using red and blue borders can appear to line up with the axes and mask an error. Use four distinct hues that are none of the axis colours.
- UVs project from the face centroid, so a naive one-copy fixture straddles the tile seam and swaps the image's halves by itself.

**The new trap specific to this stage:** a unit quad in the XY plane with UVs spanning 0 to 1 is very close to what the projection already produces, so such a fixture would look correct whether or not the stored UVs were read. **The model you render must have imported UVs that visibly differ from its projection**, for example a UV layout that maps a sub-rectangle of the image onto the face, or one rotated 90 degrees relative to the plane basis.
