# M7.6c: Smart-select, selection set operations, and vertex selection

**Status:** design
**Milestone:** M7.6c (Phase 2.5, Interaction parity)
**Predecessor:** M7.6b Inference, construction guides and on-canvas measurement, shipped v0.11.0
**Target:** v0.12.0
**Issues closed:** #37, #38, #36, #39

## 1. Context

M7.6 was split into three sub-milestones during its design, because it spanned a
kernel change, a schema change and selection semantics, and was wider than M7.5
was before its own split. M7.6a delivered the kernel half, `HalfEdgeMesh::split_face`
and the tools that drive it. M7.6b delivered the interaction half, inference,
construction guides and the measurement readout, and took `.pluton` to
`schema_version` 8. M7.6c is the third and last: selection semantics. It closes
M7.6, and with it Phase 2.5.

It is also the milestone that finally retires four M4b carry-overs. #37, #38, #36
and #39 have been open since v0.1.1 and have accumulated the dependencies they
were waiting on: materials arrived in M5, tags in M5c, and the adjacency queries
#37 names have been on `Scene` since M3.

Unlike its two predecessors this milestone changes no kernel code and no file
format. `.pluton` stays at `schema_version` 8. Everything here is Python above
machinery that already exists. That is the reason it is last: it is the only
third of M7.6 that could not have gone first.

Three facts about the existing code shape the whole design, and each was read
out of the repository rather than assumed.

**Double-click is already taken.** `SelectTool.on_mouse_double_click`
(`select_tool.py:246`) edits a label's text when an annotation is under the
cursor, and otherwise enters the instance under the cursor. #37's "double-click a
face" therefore cannot simply own the gesture; it has to dispatch behind both.
This turns out to match SketchUp exactly, where a double-click on a group enters
it and raw geometry is what you double-click once you are inside, so the
collision resolves into an ordering rather than a conflict.

**Qt has no triple-click event.** `QEvent::MouseButtonDblClick` exists; a third
press arrives as an ordinary `MouseButtonPress`. Triple-click needs its own run
counter against a clock. M7.6b already established the pattern the counter must
follow: `inference.py:283` is the codebase's only wall-clock call site, injected
so that dwell is a value in tests rather than a timer.

**`selection_vertices` is a chokepoint.** `transform_support.py:16` unions each
selected edge's endpoints and each selected face's loop into one ordered vertex
list, and Move, Rotate and Scale all read it and nothing else. Adding
`selection.vertices` to that union is what makes a bare vertex draggable in all
three tools, which is the feature #36 names as its own motivation.

## 2. Scope

### 2.1 The pure operations module

A new module `python/pluton/selection_ops.py`, beside `selection.py`. It imports
no Qt, mutates no `Selection`, and knows nothing about menus. Every function
takes ids plus a scene or model and returns ids, so each is directly callable in
a test with no widget, no model and no `QApplication`.

This mirrors M7.6b's `snap_candidates.py` / `snap_engine.py` split, and for the
reason that split earned during implementation: tests that called the pure
generators directly discriminated against broken implementations, while tests
routed through the widget masked defects. Six of M7.6b's stated mutants failed to
discriminate, and the usual cause was an assertion running through a layer that
absorbed the fault.

The module also removes a duplication hazard before it exists. The same
connected-component walk feeds triple-click and `grow`; one copy means they
cannot drift. The milestone's predecessor shipped `_GUIDE_KINDS` in three copies
and that is filed as part of #124.

**Neighbour queries**, one per direction of the click matrix:

- `bounding_edges(scene, face_ids) -> set[int]`, the union of `scene.face_edges`
  over the input.
- `adjacent_faces(scene, edge_ids) -> set[int]`, the union of `scene.edge_faces`,
  dropping the `None` that a naked edge yields on one or both sides.
- `incident_edges(scene, vertex_ids) -> set[int]`, every live edge with one of
  the given vertices as an endpoint.

Each skips ids whose entity is no longer live, matching how `selection_vertices`
already tolerates a stale id rather than raising.

**The transitive walk:**

- `connected_component(scene, seed_vertex_ids) -> tuple[set[int], set[int], set[int]]`,
  returning `(vertices, edges, faces)`. Breadth-first over the vertex adjacency
  built from live edges. An edge is included when both endpoints are reached; a
  face is included when its whole loop is reached.

This is the walk `follow_me_tool._order_path` performs at
`follow_me_tool.py:227`, lifted into one place.

**Set operations:**

- `invert(model, selection, *, select_vertices) -> tuple[set[int], set[int], set[int], set[int]]`,
  returning `(edges, faces, instances, vertices)`: the `select_all_ids(model)`
  universe minus what is currently selected, plus, when vertex mode is on, the
  active mesh's live vertices minus the selected ones. It is the one function
  here that takes the `Selection` object, which it reads and never mutates.
  Anchoring the universe to
  the function `select_all` already uses keeps the two consistent by
  construction, and it means annotations stay out of invert exactly as they stay
  out of Select All today.
- `grow(scene, *, edges, faces, vertices) -> tuple[set[int], set[int], set[int]]`
  adds, per kind, every entity sharing a sub-entity with a selected one: faces
  sharing an edge with a selected face, edges sharing a vertex with a selected
  edge, vertices sharing an edge with a selected vertex. Kinds do not bleed into
  one another, so growing a face selection never silently produces loose edges
  the user did not ask for.
- `shrink(scene, *, edges, faces, vertices) -> tuple[set[int], set[int], set[int]]`
  removes every selected entity having at least one neighbour, by the same
  per-kind adjacency `grow` uses, that is not itself selected. This is standard
  erosion and the exact inverse of `grow` on an interior region.

Both take and return `(edges, faces, vertices)` in that order and never see
instances or annotations, which have no geometric adjacency to walk. Both are
pure: they read the three sets and return three new ones.
- `same_material(scene, face_ids) -> set[int]`, every live face carrying any
  material any seed face carries. `Scene` keeps `_face_materials_front` and
  `_face_materials_back` separately (`scene.py:205`); a match on **either** side
  counts, because a user asking for "same material" means the paint they can
  see, and they cannot see which side dictionary it came from.
- `same_tag(model, instance_ids) -> set[int]`, every instance in the active
  context whose `tag_id` is one a seed instance carries. Tags live on
  `Instance.tag_id` only, never on faces or edges, so this function takes the
  model rather than the scene and returns instances rather than geometry.

### 2.2 The click matrix

`Tool` gains `on_mouse_triple_click(event, snap)`, a default no-op, symmetric
with the `on_mouse_double_click` already on the protocol at `tool.py:150`.
`ViewportWidget` synthesizes it, because Qt never will.

`SelectTool.on_mouse_double_click` keeps its two existing branches in order,
annotation first then instance, and falls through to a new geometry branch:

| Under the cursor | Double-click selects | Triple-click selects |
|---|---|---|
| Face | the face plus its bounding edges | the whole connected component |
| Edge | the edge plus its adjacent faces | the whole connected component |
| Vertex (mode on) | the vertex plus its incident edges | the whole connected component |
| Instance | enters it (unchanged) | unchanged |
| Annotation | edits a label's text (unchanged) | unchanged |

The rule underneath: a double-click adds the entity's immediate neighbours one
dimension up and down; a triple-click closes that walk transitively. Shift
composes with both, adding to the selection rather than replacing it, exactly as
it already does for a single click and for box-select.

`on_mouse_triple_click` seeds `connected_component` from the picked entity's
vertices, whichever kind was picked, and replaces or adds all three returned
sets. The vertices are kept in the result only when vertex mode is on; with the
mode off the flood returns edges and faces and the vertex set is discarded, so a
user who has never turned the mode on never acquires a vertex selection by
accident.

### 2.3 The multi-click detector

A small pure class, constructed with an interval and an optional `now_ms`,
holding the last press position, the last press timestamp and a run count.

`press(x, y, now_ms) -> int` returns the run length: 1 for a fresh run, 2 for a
double, 3 for a triple, and it saturates rather than continuing past 3, so a
fourth rapid click restarts at 1 rather than producing a run nothing handles.

A press continues the current run when it lands both within the interval of the
previous press and within `_MOVE_TOLERANCE_PX` of it. The distance test matters:
without it, two deliberate clicks on opposite corners inside the interval read as
a double-click on the second corner.

The interval defaults to `QApplication.doubleClickInterval()`, read once at
construction so the gesture honours the user's system setting, and stored as a
plain number. Qt is touched exactly once, at the boundary; the class itself has
no Qt import and no clock of its own, which is what makes the whole gesture a
value in tests.

`ViewportWidget` owns one detector. Its `mousePressEvent` calls `press` and
dispatches `on_mouse_triple_click` on a return of 3. Qt's own
`mouseDoubleClickEvent` continues to drive `on_mouse_double_click` unchanged, so
the double-click path is not re-implemented on top of the counter and existing
behaviour carries no risk from this change.

### 2.4 What the flood crosses

The flood walks the **active context's mesh only**. It does not descend into a
nested instance and does not escape to the parent, matching how
`pick_selectable`, `pick_annotation` and `select_all_ids` all already scope
themselves. An instance resting on flooded geometry is not reached.

Connectivity is through **shared vertices**, not shared edges. Two faces meeting
at a single corner form one component. This is the more inclusive reading, and it
is what makes the flood's result independent of which entity kind seeded it,
which is in turn what makes double-click and triple-click compose predictably.

### 2.5 Vertex selection

`Selection` gains `_vertices` alongside its existing four sets, with matching
`replace`, `add`, `remove`, `toggle_vertex` and `clear` handling.

The addition is mechanical. Its four consumers are not, and each is a correctness
site:

1. **`selection_vertices` (`transform_support.py:16`)** unions
   `selection.vertices` into its result. This single line is what makes Move,
   Rotate and Scale drag a bare vertex, since all three read that function and
   nothing else.
2. **`prune_to_live` (`selection_controller.py:30`)** gains a vertices line.
   Without it, an undo that deletes geometry leaves dangling vertex ids in the
   selection, which is #46 reintroduced in a new kind.
3. **`counts()` returns five numbers** and `selection_status_text`'s labels
   tuple gains `"vertex"`. Its `zip(..., strict=True)` turns a missed update into
   a loud failure rather than a silent truncation.
4. **`_on_delete_selection` (`main_window.py:947`)** needs the rule in D6 below.

### 2.6 Vertex mode, picking and the glyph

The mode is `ViewportWidget.select_vertices`, default `False`, exposed through
`ToolContext.select_vertices_provider` and toggled from a `View` menu checkbox.
This copies `show_guides` deliberately: same rail, same provider-is-`None`-means-
the-default convention that lets a bare test `ToolContext` keep today's
behaviour, same menu.

`pick_selectable` gains a `select_vertices=False` keyword. When set, it tests
vertices first, at the existing `PICK_PIXEL_TOLERANCE` of 8 px, and returns
`("vertex", id)` on a hit before considering edges. With the flag unset the
function is byte-for-byte today's behaviour, which is the property that keeps the
entire existing selection test suite meaningful.

`entities_in_box` returns **three** sets rather than two, the vertex set empty
unless the flag is on. A fixed arity rather than a conditional one means its one
caller (`select_tool.py:177`) and its tests change once, visibly, rather than a
`len()` check drifting later.

The glyph paints in the 2D QPainter layer next to the annotations: a small filled
square at each selected vertex's projected position, clipped to the viewport.
There is no point rendering anywhere in the codebase, no `GL_POINTS` and no
`glPointSize`, so the alternative would be a new GL pipeline. The QPainter layer
has no depth buffer, so a selected vertex behind a wall draws on top of it. This
is a known and accepted difference from how selected edges and faces render, and
it matches what snap markers already do.

### 2.7 Set operations, wired

Five handlers on `MainWindow`, each a three-liner: call `selection_ops`, call
`Selection.replace`, refresh the status text, repaint.

`build_context_menu` gains a `Select` submenu carrying **Grow**, **Shrink**,
**All with Same Material** and **All with Same Tag**, which is where a SketchUp
user right-clicks for them. `Edit` gains **Invert Selection** beside the existing
Select All, because invert needs no entity under the cursor.

Entries are **greyed out, not hidden**, when their precondition fails:
`same_tag` needs a selected instance, `same_material` a selected face, and
`grow` and `shrink` a non-empty selection. The menu's shape stays constant under
the cursor.

### 2.8 Issue #39

The smallest piece in the milestone. `_box_rect_ndc_segments`
(`scene_renderer.py:1140`) emits four solid edges today. In crossing mode each
edge is subdivided into dashes at a fixed pixel period before conversion to NDC,
so the dash length is stable on screen rather than varying with the rectangle's
size. Colour continues to distinguish the modes as it does now; the dash is
additive, matching SketchUp's solid-for-window, dashed-for-crossing convention.

## 3. Module layout

```
python/pluton/selection_ops.py          NEW  pure ops: neighbours, flood, set operations
python/pluton/viewport/click_runs.py    NEW  pure multi-click run counter
python/pluton/selection.py              +vertices set, toggle_vertex, counts() -> 5
python/pluton/tools/tool.py             +on_mouse_triple_click, +select_vertices_provider
python/pluton/tools/select_tool.py      geometry branch on double-click, triple-click handler
python/pluton/tools/transform_support.py  selection_vertices unions selection.vertices
python/pluton/viewport/picking.py       pick_selectable(select_vertices=), entities_in_box -> 3
python/pluton/viewport/viewport_widget.py  owns the detector, synthesizes the triple-click hook,
                                        select_vertices attribute, paints the vertex glyph
python/pluton/ui/selection_controller.py  prune_to_live gains vertices; status text gains "vertex"
python/pluton/ui/context_menu.py        Select submenu
python/pluton/ui/main_window.py         five handlers, Edit > Invert, View > Select Vertices
python/pluton/viewport/scene_renderer.py  dashed crossing rectangle
```

`selection_ops.py` imports `pluton.scene` and nothing above it. `click_runs.py`
imports nothing from pluton at all. Neither imports Qt. `SelectTool` imports
`selection_ops` downward, which is why the operations do not live in
`selection_controller.py`: that module sits in `pluton/ui/`, and a tool reaching
up into the UI layer to get its click semantics would invert the layering.

## 4. Testing

Every `selection_ops` function is tested by **direct call** against a hand-built
`Scene`: no widget, no model where a scene will do, no `QApplication`. M7.6b's
evidence is the reason this is stated as a requirement rather than a preference.

The multi-click detector is tested by feeding it timestamps. No test in this
milestone sleeps, and no test reads a real clock.

Beyond the per-function tests, three properties get explicit coverage:

1. **`shrink` inverts `grow`** on an interior region: growing then shrinking a
   selection whose boundary is untouched returns the original set.
2. **The flood is seed-kind independent**: seeding `connected_component` from a
   face, from one of its edges, and from one of its vertices produces identical
   results.
3. **`pick_selectable(select_vertices=False)` is unchanged**: the regression gate
   for the highest-risk change in the milestone.

Each test must be shown to **fail** against a named broken implementation, proven
by building that mutant, not by asserting it would fail. Six of M7.6b's stated
mutants turned out not to discriminate, and that was discovered only because
implementers built them.

## 5. Decisions

**D1. Pure operations module rather than methods on `Selection` or the
controller.** `Selection` is transient state with no scene reference and should
not grow a scene dependency. `selection_controller` is in the UI layer. A
Qt-free, model-light module is directly testable and importable from both
callers.

**D2. `ViewportWidget` synthesizes the triple-click; `SelectTool` never sees a
clock.** Timing lives at the Qt boundary where Qt events already arrive. The tool
receives a semantic event. Any future tool wanting triple-click gets it free.

**D3. Qt's `mouseDoubleClickEvent` keeps driving `on_mouse_double_click`.** The
run counter is used only to detect the third click. Re-implementing double-click
detection on top of the counter would put every existing double-click behaviour,
including entering a group, at risk for no gain.

**D4. Vertex picking is opt-in and off by default.** Extending the
thin-target-wins rule to vertices unconditionally would change what every click
near a corner selects, across every tool that picks, on geometry that is mostly
corners. SketchUp exposes no direct vertex selection at all, partly for this
reason. The mode makes the change something the user asks for.

**D5. The flood keeps vertices only when vertex mode is on.** A user who has
never enabled the mode cannot acquire a vertex selection by accident, and so
cannot be surprised by a Move that drags vertices they cannot see selected.

**D6. Delete ignores selected vertices.** `Scene.remove_vertex` exists, but a
vertex with incident edges cannot be removed without cascading into those edges
and the faces they bound. A Delete that destroys two faces because one corner was
selected is the same trap M7.6b closed for hidden guides. A vertex-only selection
makes Delete a no-op; a mixed selection deletes the edges and faces and leaves
the vertices, which `prune_to_live` then drops if they died with their geometry.

**D7. `invert` reuses `select_all_ids`'s universe.** Inventing a second universe
would guarantee eventual divergence between Select All and Invert. The visible
consequence is that annotations are excluded from both, which is today's Select
All behaviour and therefore not a new asymmetry.

**D8. `same_material` matches on either side.** Front and back are separate
dictionaries in `Scene`, but a user cannot see which dictionary the paint they
clicked came from.

**D9. `same_tag` returns instances, `same_material` returns faces.** Tags live on
`Instance.tag_id`; materials live per face. The two operations therefore operate
on different kinds, and the spec says so rather than pretending to a symmetry
that the data model does not have.

**D10. `grow` and `shrink` do not cross entity kinds.** Growing a face selection
yields faces, never the loose edges around them. Cross-kind growth is what
double-click already does, deliberately and one step at a time.

**D11. Menu entries grey out rather than hide.** A menu whose entries appear and
disappear under the cursor is harder to learn than one whose entries are
sometimes unavailable.

**D12. `entities_in_box` returns a fixed three-tuple.** A conditional arity
invites a caller to test `len()` and drift.

**D13. The vertex glyph has no depth test.** Accepted, consistent with snap
markers, and cheaper than a new GL point pipeline by a wide margin.

**D14. No kernel change, no schema change.** `.pluton` stays at
`schema_version` 8 and `ctest` is expected to stay at 135. Everything in this
milestone is Python above existing machinery.

## 6. Out of scope

- **Soft and smooth edges.** pluton has no soft-edge concept, so the flood has no
  smoothing boundary to respect. If soft edges arrive, the flood gains an option
  rather than a rewrite.
- **Vertex-level topology editing** beyond dragging: no weld, no collapse, no
  split-at-vertex. #36 asked for selection and drag; those arrive, and nothing
  more.
- **Selection by any other predicate.** Only material and tag, the two #38 names.
  Not by area, not by normal direction, not by entity type.
- **Selection memory or named selection sets.** Not requested anywhere.
- **Center inference**, still blocked on #35 modelling circles and arcs as
  logical curve entities. Deferred during M7.6b's design and not revisited here.

## 7. Risks

**The picking change is the milestone's real risk.** `pick_selectable` is read by
every tool that picks. The mitigation is the default-off flag plus an explicit
regression test asserting the unchanged path, and the fact that with the flag
unset no new code executes at all.

**The double-click fall-through could shadow entering a group.** The geometry
branch runs only after the instance pick returns `None`, so a double-click on an
instance still enters it. The test that pins this is worth writing before the
branch exists, because it fails silently in the direction users will notice most.

**The multi-click run counter can mis-fire on a slow machine** if a legitimate
double-click's second press lands outside the interval. This is Qt's own risk,
already present for `mouseDoubleClickEvent`, and reading the interval from
`QApplication.doubleClickInterval()` rather than hard-coding it means pluton
inherits whatever the user has configured.

**`grow` and `shrink` have no SketchUp equivalent**, so there is no reference
behaviour to check against. The inverse-property test in section 4 is the
substitute: it pins them against each other rather than against a memory of
another application.

## 8. Sequencing

1. `selection_ops.py` with the three neighbour queries and `connected_component`,
   tested by direct call.
2. `click_runs.py`, tested with injected timestamps.
3. `Tool.on_mouse_triple_click` plus `ViewportWidget` synthesis and dispatch.
4. `SelectTool`'s geometry branch and triple-click handler, for faces and edges
   only. **At this point #37 is complete and shippable on its own.**
5. `Selection.vertices` and its four consumers, including D6's Delete rule.
6. Vertex mode, `pick_selectable(select_vertices=)`, `entities_in_box`'s third
   set, and the vertex row of the click matrix.
7. The vertex glyph.
8. The five set operations in `selection_ops`, tested by direct call.
9. Menu wiring: the `Select` submenu, `Edit > Invert Selection`, `View > Select
   Vertices`, and their enable rules.
10. #39's dashed crossing rectangle.

Step 4 is a natural halt point: #37 is closed, nothing is half-built, and no
schema or picking behaviour has changed yet.
